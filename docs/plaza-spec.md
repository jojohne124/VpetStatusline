### 實作後發現、規格沒寫到的

- **合成必須在 dot 層做，不能在 cell 層。** sprite 貼到奇數 y 時會跨半個 cell，
  在 cell 層貼會遇到半格問題。改成「拆成 dot → 貼 → 打包回 cell」就完全不用處理奇偶。
  另一條路是限制 y 只能是偶數，但那會讓垂直移動的最小單位變成 2 dot、與水平的
  1 dot 不對稱，走起來會怪。（見 `src/daemon/plaza.js` 開頭）
- **角色美術有大量不透明黑**（agumon IDLE_1 的 256 個 dot 裡有 81 個純黑）。
  家裡因為底盤是深色所以看不出來，廣場一旦鋪上底圖，黑色outline 會變成明顯的黑框。
  第一期沒有底圖所以不影響，**上底圖前要先決定黑色要不要當透明處理**。
- **名牌走文字層、不進 dot 緩衝** —— 名牌要支援中文，一個字佔一整個 cell，沒有
  dot 級字模。沿用 PvP 名牌「渲染成 ANSI 之後才貼字」的分層。
- **名牌會穿透**（2026-08-20 已修）：文字層不在 painter's algorithm 裡，要另外用
  owner 緩衝判斷遮擋。詳見 §五「名牌」。
- **名牌位置試了四版才定案**（腳下 → 上下自動選 → 一律頭上 → 一律腳下 + 底部保留）。
  中間那版「放不下就改標頭上」看數字很漂亮（顯示率 92~98%），但實際看畫面時名牌會
  隨走動上下跳，**比不見還難讀** —— 數字好不代表畫面好，這種只有看了才知道。
- **走路節奏第一次實測就不對**：停留 37%、單人一小時只走訪 486 格，看起來像一群角色
  在原地磨蹭。原因是「固定 4 拍走 4 dot」讓每個人被綁在自己起點的 4-dot 晶格上，
  加上撞牆整段作廢。改成分段走法 + 撞牆反彈後是 12% / 1881 格。
  **這正是先做預覽鷹架才划算的地方** —— 這兩個數字接完整套才發現的話，
  修起來要動的東西多得多。

## 一、範圍

### 本期要做

- 玩家把自己的 vpet 送到一個**全玩家共用的廣場**
- 廣場是一個**矩形空間**，vpet 在裡面隨機上下左右走動
- **所有人看到的畫面一致**（同一時刻、同樣的位置）
- vpet 外出期間，家裡（statusline / daemon）顯示「不在家」，並**暫停互動與飼育**
- 回家後一切恢復

### 本期不做（列出來是為了避免設計時被牽著走）

| 項目 | 為什麼延後 |
|---|---|
| 聊天 / 對話框 | 需要強一致的儲存（Durable Object），牽涉付費方案與治理成本 —— 見附錄 A |
| 角色之間的碰撞 | 第一版允許互相穿過，不影響可行性驗證 |
| 互動（打招呼、對戰邀請） | 等基礎穩定 |
| 廣場內的道具 / 場景物件 | 同上 |

**第一期的目的是驗證兩件最不確定的事**：多人走動的同步看起來對不對、y 排序的畫面好不好看。這兩件事不需要聊天就能驗。

## 二、核心設計：決定性模擬（為什麼「畫面一致」不難）

現有架構的走路是純函數（`agumon-core.js:computeWalk`），這是當初為了「多視窗算出同一畫面」刻意設計的，同一個決定也讓多視窗算出同一場戰鬥。

廣場沿用同一招：

> **伺服器只存「誰在場」的名單，不推進任何位置。**
> 每個 client 用同一個純函數，各自算出**所有人**的位置。

因此不需要伺服器逐拍 tick、不需要 WebSocket、不需要狀態同步協定。這是本設計最重要的一點，也是成本能壓下來的原因。

### 一致性的三個前提

1. **同樣的輸入** — 名單裡每個人的 `seed` 與 `joinedAt` 由伺服器決定並廣播，不由 client 自己產
2. **同樣的函數** — 走路演算法放在 `src/shared/`，client 與（未來的）伺服器共用同一份
3. **同樣的時間** — 見下節

### 時鐘同步

各機器的系統時鐘可能差好幾秒。每次 poll 伺服器在回應帶上自己的 `serverNow`，client 記下偏移：

```
clockSkew = serverNow - localNow        // 每次 poll 更新
step      = floor((Date.now() + clockSkew) / 1000)
```

1 拍 = 1 秒，對齊到秒以內即可，不需要 NTP 等級的精度。

## 三、走路演算法

### 選定做法：任意斜率的「一段路」+ 增量快取

一次抽一段路（方向向量 + 長度），段內每拍走 1 dot，走完再抽下一段。

```
STEP_MS     = 750                  // 一拍多長（家裡是 1000ms，見下）
DIR_VECTORS = 分量 |v| <= 3 的互質向量，共 32 個（例如 1:0、3:1、2:3）
RUN_MIN/MAX = 6 ~ 34               // 一段路走幾拍（連續整數）
STAY_MIN/MAX= 4 ~ 8                // 停一次幾拍
STAY_CHANCE = 1/4                  // 抽中「停」的機率（換算成時間約 12%）

第 k 段：dir = DIR_VECTORS[hash(seed, 3k+1)]、len = hash(seed, 3k+2)
段內位置用 Bresenham 一次算出（主軸每拍 1 dot，副軸按比例四捨五入）
```

演算法改過兩次，兩次都是**看了畫面才發現問題**，這正是先做預覽鷹架的價值：

| 版本 | 做法 | 問題 | 一小時走訪 | 停留時間 |
|---|---|---|---|---|
| v1 | 每 4 拍走 4 dot，撞牆整段作廢 | 碎步磨蹭；貼邊的角色一直「決策了但沒動」像卡住，空轉還全被計進停留 | 486 格 | 37% |
| v2 | 一次抽一段路（上下左右 + 四斜向），撞牆反彈 | 範圍夠了，但**軌跡只有 8 種角度**，放久了整張圖是水平/垂直/45° 線疊出來的網格，像在走既定路線 | 1881 格 | 12% |
| v3 | 有理斜率（32 個互質向量）+ Bresenham，段長連續整數，走到牆邊就停、下一段重抽 | — | 1700 / 2673 格（64%） | 12.7% |

三個關鍵改動的理由：

**有理斜率。** v2「只有 8 種角度」是網格感的根因 —— 每段都是完美直線，疊久了必然
只剩那幾條線。改用互質向量（(3,1)、(2,3)…）配 Bresenham，角度從 8 種變 32 種。
**刻意不用 cos/sin 取連續角度**：那會引入超越函數，而 `Math.sin/cos` 的精確值不在
IEEE754 的保證範圍內（不同引擎可能差 1 ulp）。整個廣場的前提是每個 client 算出
**位元級相同**的結果，不能賭這個。互質向量 + Bresenham 全程整數。

**段長改成連續整數。** v2 的清單 `[4,6,8,12,16,20]` 全是偶數，導致每段終點永遠落在
同一個奇偶晶格上，轉彎點跟著規律化。

**撞牆從反彈改成「走到牆邊就停、下一段重抽方向」。** 固定方向的反彈會走出撞球檯般的
週期軌跡，反而強化單一感。順帶讓「最長段不得超過場地」這條隱形限制消失 ——
縮小場地不會再穿牆。（極端情況：已貼牆且朝外一步都走不了 → 掉頭走同一條線，
不當成「停」，否則貼牆很常見會把停留比例灌水到 21%。）

**停留時間佔比約 12%。** 注意「抽中停的機率」（1/4）與「站著的時間佔比」差很多 ——
一段路平均 15 拍、一次停平均 6 拍。**停下時角色仍持續演 IDLE_1/IDLE_2** ——
v1 停下時鎖 IDLE_1，連動畫都停掉，看起來像畫面當掉而不是站著休息。

- 位置從 `joinStep` 起一段一段累加，界限見 §五（頂/底其中一邊要留給名牌）
- 橫越 96 dot 寬的廣場約需 3~5 段 ≈ 70 秒，是刻意的慢步調

**一拍 750ms 而不是 1000ms。** 家裡那 1000ms 是被 Claude Code 的
`statusLine.refreshInterval`（最快 1 秒）綁住的，不是美感選擇；廣場只在 daemon 的
瀏覽器畫面跑，沒有那個限制，所以拍子可以更細、走起來更順。
⚠️ `STEP_MS` 是**時間契約的一部分** —— 所有 client 都要用同一個值把牆鐘換成 step，
單邊改就等於改變別人眼中你的走路速度。前端輪詢刻意比一拍更密（`STEP_MS / 3`），
免得輪詢與拍子產生節拍差（同一拍畫兩次 / 跳過一拍）；合成 20 人約 0.3ms，可忽略。

> 這組數字**預期要微調**。先跑起來看畫面，再決定停留權重與速度。

### 為什麼可以用累加（而不是閉合公式）

累加需要從進場重播，看似 O(n)。實際算一下：待一小時 ≈ 3600 拍 ÷ 平均段長 15 ≈ **240 段**，每段幾個 hash。20 個人也才幾千次，一秒一次，可忽略。

而且 client 端**只在第一次計算時重播**，之後每拍只推進差量（快取 `{step, x, y}`）。重開視窗才會重播一次。

用整數格子累加，沒有浮點誤差累積的問題，任何 client 從任何時間點重播都得到完全一樣的結果。

### 為什麼不用「隨機路標 + 內插」

考慮過 `waypoint(k) = hash(seed,k)` 落點再內插的做法，它是 O(1) 且保證不出界，但：

- 兩個路標可能相隔整個廣場，內插會變成「等速滑行」，速度隨距離變動，不像走路
- 要讓速度固定就得讓停留時間正比於距離，那又變回累加

格子走位在像素風格下更自然（原版電子雞也是格子移動），且與現有「1 拍 1 步」的節奏一致。

### 面向

只有左右兩種（`getFacingRows` 是水平翻轉，沒有背面/正面幀）。

- `dir` 有水平分量（含斜向）→ 更新面向
- 純上 / 下 / 停 → **維持前一個面向**

這是美術限制。要真的有背面得補幀，不在本期。

⚠️ 轉身要等**真的邁出第一步**（段內第 1 拍）才生效。段的第 0 拍畫的其實是上一段的
終點、位置還沒動，那一拍就套新方向會讓角色在最後一步往右走的同時臉朝左，
每次轉向都閃一格反向。

## 四、資料模型與協定

### 在場紀錄

```json
{
  "code":     "阿張",              // 名牌（沿用 PvP 的 code，同一套身分）
  "char":     "zephagamon_ace",   // 角色 id，讓別人畫得出來
  "stage":    "Super-Ultimate",
  "seed":     1739284,            // 伺服器產生，決定走路路徑
  "joinedAt": 1786900000000       // 伺服器時間；決定走路起點，也是 MAX_STAY 的計時基準
}
```

`seed` 與 `joinedAt` **必須由伺服器決定**。若由 client 自報，兩個 client 對同一個人的路徑計算就可能不同（也可被竄改）。

### 端點（沿用現有 Worker，`server/pvp/worker.js`）

| 方法 | 路徑 | 說明 |
|---|---|---|
| `POST` | `/plaza/join` | 進場。body 帶 `code` / `char` / `stage`；回傳分配的 `seed`、`joinedAt` |
| `POST` | `/plaza/leave` | 離場，立即移除 |
| `GET` | `/plaza/state` | 取得在場名單 + `serverNow` |

沿用現有的 `X-Pvp-Key` 驗證。

### 儲存：只在 join / leave 時寫入

在場名單存**單一 key**（`plaza:roster`），不是每人一個 key —— `GET /state` 只要一次讀取。
讀取免費額度 10 萬/日，輪詢再頻繁都不是問題。**瓶頸只在寫入（1000/日，與 PvP 戰卡共用）。**

#### 心智模型：持久狀態，不是連線 session

這是本節最重要的決定。廣場的「在場」是**持久狀態**，不是要持續證明自己活著的連線：

> vpet 就是在外面，直到你叫牠回家。

與 `_forceSleep`、`_freezeEvolve` 同一類 —— 設定了就一直有效，關掉 daemon 也不會變。
因此**不需要心跳**，只在 `join` / `leave` 時寫入。

曾設計過 90 秒心跳制，但那是「聊天室在線中」的思路，廣場不需要知道你正在看。
心跳制的代價是寫入量 = 人數 × 時數 × 3600 ÷ 間隔，10 人在線 2 小時就要 800 writes/日，
逼得同時在線只能開到 10 人 —— 那個上限是心跳制的產物，不是真實限制。

| 模式 | 寫入量 | 幽靈殘留 |
|---|---|---|
| 90 秒心跳 | 10 人 × 2h = **800**/日 | 3 分鐘 |
| 30 分心跳 | 10 人 × 2h = 40/日 | 60 分鐘 |
| **join / leave** | 30 人 × 每天進出 10 次 = **600**/日 | 見下 |

#### leave 送不到怎麼辦

`leave` 在當機／斷電／SIGKILL 時送不出去。三個補救，**都不需要額外寫入**：

1. **讀取時過期** — `GET /state` 直接濾掉 `joinedAt` 超過 `MAX_STAY` 的條目。
   過濾是在回應時算的，不寫 KV。
2. **順手清理** — 有人 join / leave 時本來就要寫，那次順便把過期條目移除。免費。
3. **滿了先清過期再判斷** — 人數判定是在濾掉 `MAX_STAY` 過期條目之後才做，
   所以殭屍不會長期佔住名額。清完仍滿才拒絕。

`MAX_STAY` 暫定 **24 小時**：夠長，正常使用不會被誤踢；也夠短，忘了回家的隔天會自己回去。

#### client 端要對齊

daemon 啟動時若 `state.plaza` 存在 → 先 `GET /state` 確認自己還在名單裡。
不在（被 `MAX_STAY` 清掉了）→ **本機也要回家**，否則會出現「家裡顯示不在家、
廣場上卻沒有你」的鬼打牆。這是一次讀取，免費。

`leave` 仍要盡力送（daemon 收到 SIGINT / SIGTERM 時），但**正確性不依賴它**。

#### 這樣放棄了什麼

無法得知某人的 client 是否真的在執行。第一期只是走路，不需要這個資訊。
第二期聊天會需要，但聊天本來就要上 Durable Object，DO 有常駐連線自然就有。

#### 採用值

| 參數 | 值 |
|---|---|
| 寫入時機 | 只有 `join` / `leave` |
| `MAX_STAY` | 24 小時（讀取時過期 + 寫入時順手清） |
| 同時在線上限 | **20 人**（由畫面可讀性決定，不再是額度決定） |

> KV 的最終一致性（跨區傳播最久 60 秒）對「誰在場」可以接受 —— 晚半分鐘看到有人
> 進場不影響體驗。聊天就不行，那是第二期要換 DO 的另一個原因。

## 五、渲染

### 舞台

單位換算：1 個 cell = 1 dot 寬 × 2 dot 高；1 dot 在畫面上是 8 × 8 px 的正方形。
所以**視覺上的正方形 = dot 數相等**，不是 cell 數相等。

| | 現況（家裡） | 廣場 |
|---|---|---|
| dot | 52 × 16 | **96 × 48**（2:1） |
| cell | 52 欄 × 8 列 | 96 欄 × 24 列 |
| 畫面 | 416 × 128 px | **768 × 384 px** |

原本定 96×96 正方形（768×768），實際看過之後分兩次改矮到 48 —— 瀏覽器裡連表頭都要
捲動才看得完。注意「視覺正方形」是 **dot 數**相等而不是 cell 數相等
（1 cell = 1 dot 寬 × 2 dot 高），這點很容易搞錯。

改場地只要動 `plaza-walk.js` 的 `PLAZA_W` / `PLAZA_H`，其餘（合成、名牌位置、
畫布尺寸、測試）全部從那裡推導。

**可走範圍不等於場地**：底部要保留一個 cell 列（`LABEL_RESERVE`）給名牌，
所以 `y ∈ [0, PLAZA_H - SPRITE - 2]`。沒有這段保留區的話，角色走到最底時腳下那一列
已經在畫面外，名牌會整個消失。

`#stage` 目前是 `width:fit-content` + `min-width:416px`（見 `daemon.js` 該段註解），
廣場模式要能撐到 768 px。

### y 排序合成器（本期最大的一塊新程式）

現有 `renderCells` 是把一排排 cell 攤平輸出，沒有「把 sprite 貼到 (x,y)」的概念。需要新增：

1. 建一張 `plazaW × plazaH` 的空 cell 緩衝
2. 把所有 vpet 依 **y 由小到大**排序（y 大的後畫 → 蓋在前面，painter's algorithm）
3. 逐一貼上（含名牌）
4. 交給既有的 `renderCells` 輸出

### 名牌

角色腳下顯示 `code`。PvP 已有「腳下名牌」的先例（`2799390 PvP 強化：固定練習對手、雙方腳下名牌`），沿用同一套。

名牌走**文字層**（整張圖渲染成 ANSI 之後才貼字），因為名牌要支援中文，一個字佔
一整個 cell，沒有 dot 級字模。代價是它不在 painter's algorithm 裡，預設會浮在所有人
身上 —— 後排的名字蓋在前排的身體上，前後關係整個看反。

**解法：合成時多維護一張「這個 dot 是誰畫的」緩衝**（`owner`），名牌要佔的那幾格若
被 z 較大（站得比較前面）的人畫過，整條名牌就不顯示。切一半更難看，所以是整條省略。
同一列多人重疊時也改成保留前排那個，與遮擋規則一致。

實測名牌顯示率：5 人 91%、12 人 66%、20 人 50%。人多時掉得明顯，
若之後覺得不能接受，下一步是「腳下被擋就改標在頭上」。

### 對手角色本機沒安裝

**已經解決過**：PvP 的黑影 fallback（`91ce825`）。廣場直接沿用 —— 讀不到角色資產就用 Shadow 剪影，不要拒絕顯示。

### statusline 不顯示廣場

狀態列只有一行，二維矩形不可能塞下。**廣場是 daemon 專屬功能**，statusline 使用者只會看到「外出中」文字，想看廣場要開獨立視窗。這點需要在文件寫清楚。

## 六、「不在家」狀態

### 狀態

`state.plaza = { joinedAt, seed }`，不在廣場時不存在（比照 `mood` 的做法，預設值不落地）。

### 暫停哪些

| 功能 | 外出時 | 理由 |
|---|---|---|
| 訓練值成長 | **暫停** | 飼育行為 |
| 自動戰鬥 | **暫停** | 同上 |
| 進化判定 | **暫停** | 同上 |
| 摸摸（點角色） | **暫停** | 人不在家 |
| 閒置睡眠 | **暫停** | 在外面走動，不會在家睡 |
| `reset` / `evolve` / `battle` | **擋下**，提示先回家 | 會改變角色狀態 |
| `card` / `tree` / `album` / `bg` / `code` / `doctor` / `stats` | 照常 | 純資訊或設定，與飼育無關 |

⚠️ hook 仍會照常寫 `hook.json`（那是 Claude Code 的脈搏，我們不該擋），但 `decideAgumon` 在外出期間**不得**用它加訓練值、不得武裝自動戰鬥。這是要在既有程式碼裡加 gate 的地方。

### 家裡的演出

第一期**先做最簡單的**：空舞台中央顯示 `NOT HOME` 文字，其餘照舊（底圖仍在）。

不做美術。等整套跑起來、確定這個功能會留下來，再考慮小紙條 sprite 或角色淡出剪影。

## 七、入口

| 入口 | 動作 |
|---|---|
| `vpet plaza` | 送去廣場 + 開瀏覽器（比照 `vpet album` / `vpet bg` 的 `PLAYER_PAGES` 機制） |
| `vpet home` | 回家 |
| daemon 進階區按鈕 | 同上兩個 |

### 廣場做成 daemon 的一個模式（不另開頁面）

決定做進 daemon 頁面，用一個「家 / 廣場」切換，理由由重到輕：

1. **避免兩個寫入者。** 「在外面」是寫進 `color-state.json` 的持久狀態，而那份檔案的
   單一寫入者原則（C 方案：daemon 當家、statusLine 退唯讀）是先前花力氣建立的。
   另開一個 process 去寫同一份 state，等於把那個問題重新製造一次。
2. **不然會變成兩個視窗並排** —— daemon 顯示 NOT HOME、廣場頁顯示廣場，很蠢。
3. **可直接沿用** daemon 既有的 canvas、ANSI cell 繪製、輪詢迴圈。
4. `leave` 要在關閉時盡力送出，daemon 本來就有生命週期可掛（SIGINT / SIGTERM）。

⚠️ 但 `daemon.js` 已經 780 行且內嵌一大段 HTML template。**廣場的伺服器端邏輯
（Worker 客戶端 + 多角色合成）要抽成 `src/daemon/plaza.js`**，`daemon.js` 只留
模式切換與少量 HTML。否則會重蹈「什麼都塞進 daemon.js」的覆轍。

## 八、失敗與邊界

| 情況 | 行為 |
|---|---|
| 後端連不上 | 進場失敗並明確報錯，不要靜默留在「外出中」狀態卡住 |
| 進場後後端掛掉 | 廣場畫面停止更新並提示；**不自動回家**（在場是持久狀態，後端恢復後應該還在） |
| 名單滿 | 上限 **20 人**。滿了**回明確提示**「廣場人太多了，晚點再來」，不進場。<br>（日後可改成 vpet 在原地搖頭的表演，本期先用文字） |
| 名牌重複 | 沿用 PvP 現有行為（後者覆蓋），並在文件提醒別撞名 |
| 同一台機器開兩個 daemon | 以 `code` 為唯一鍵，後進場的取代前一筆 |

## 九、安全

- 沿用 `X-Pvp-Key`（共用金鑰，由架設後端的人發放）
- 送到後端的只有：名牌、角色 id、階級。**不含**任何本機路徑、token 用量、花費
- `code` 已是使用者自填的公開顯示名（PvP 就在用），廣場不新增個資曝險

## 附錄 A：第二期（聊天）為什麼另外算

不放進第一期的實質原因，先記下來：

1. **儲存要換** — KV 免費額度 1000 writes/日，聊天幾分鐘就燒光；且最終一致（最久 60 秒）會讓訊息亂序。需要 Durable Object（一房間一物件、強一致、可掛 WebSocket）。**DO 是否需要付費方案要先查證**，這是外部依賴，不是寫程式能繞過的。
2. **治理是持續成本** — 公開聊天 + 共用金鑰，至少要有字數上限、發話頻率限制，以及**有人能刪訊息**。這不是一次性工時。
3. **可能根本不需要** — 若第一期做完發現大家不會同時上線，第二期就沒有意義。
