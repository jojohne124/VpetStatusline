# 廣場（Plaza）規格書 — 第二版

> 狀態：**第二版已定案；第 1～3 期都已實作**（伺服器、進場離場、從邊界走入、場景鎖、隱藏幽靈對戰、聊天、對戰）。
> 對應討論：2026-08-17（第一版）／2026-08-19（第一刀）／2026-10-07（第二版：改用內網主機、加入聊天與對戰）。

## 第二版改了什麼

第一版的後端是 Cloudflare Worker + KV，所以設計被 KV 的寫入額度與最終一致性綁住：
不能有心跳、不能聊天、對戰只能是「幽靈對戰」。第二版改成**一台內網主機當伺服器**，
這些限制都不存在了。

| | 第一版 | 第二版 |
|---|---|---|
| 伺服器 | Cloudflare Worker + KV | **內網主機**（目前是 `KAIHSIANGCHANG`）上的一個 node 程式 |
| 連線設定 | 每人要 `vpet pvp-setup <url> <key>` | **不用設定**，位址內建在 release 裡 |
| 在場 | 持久狀態（關掉 daemon 也還在外面） | **跟著連線**：斷線就回到前線 |
| 進場角色 | 家裡那隻 | **前線那隻** |
| 走法 | 隨機走、出生在場內 | 全場自由走，**從隨機邊界走進畫面** |
| 聊天 | 不做（需要 Durable Object） | **做** |
| 對戰 | 幽靈對戰（另一套 `vpet pvp`） | **在廣場裡邀請，同意後開打** |
| 戰績 | — | **不記**（純娛樂，之後視情況） |
| 範圍 | 網際網路 | **只限內網** |
| 顯示端 | daemon | **只做 daemon**（statusline、mod 不顯示廣場） |

舊的幽靈對戰（`vpet pvp` / `vpet pvp-setup` / `vpet code` 的伺服器部分）**先隱藏**：
指令與說明都拿掉入口，程式碼留著不刪。見 §十。

### 第一刀實作後發現、規格沒寫到的

- **合成必須在 dot 層做，不能在 cell 層。** sprite 貼到奇數 y 時會跨半個 cell，
  在 cell 層貼會遇到半格問題。改成「拆成 dot → 貼 → 打包回 cell」就完全不用處理奇偶。
  另一條路是限制 y 只能是偶數，但那會讓垂直移動的最小單位變成 2 dot、與水平的
  1 dot 不對稱，走起來會怪。（見 `src/daemon/plaza.js` 開頭）
- **角色美術有大量不透明黑**（agumon IDLE_1 的 256 個 dot 裡有 81 個純黑）。
  家裡因為底盤是深色所以看不出來，廣場一旦鋪上底圖，黑色outline 會變成明顯的黑框。
  第一期沒有底圖所以不影響，**上底圖前要先決定黑色要不要當透明處理**。
- **名牌走文字層、不進 dot 緩衝** —— 名牌要支援中文，一個字佔一整個 cell，沒有
  dot 級字模。沿用 PvP 名牌「渲染成 ANSI 之後才貼字」的分層。
- **名牌會穿透**（2026-08-20 已修）：文字層不在 painter's algorithm 裡，要另外用
  owner 緩衝判斷遮擋。詳見 §五「名牌」。
- **名牌位置試了四版才定案**（腳下 → 上下自動選 → 一律頭上 → 一律腳下 + 底部保留）。
  中間那版「放不下就改標頭上」看數字很漂亮（顯示率 92~98%），但實際看畫面時名牌會
  隨走動上下跳，**比不見還難讀** —— 數字好不代表畫面好，這種只有看了才知道。
- **走路節奏第一次實測就不對**：停留 37%、單人一小時只走訪 486 格，看起來像一群角色
  在原地磨蹭。原因是「固定 4 拍走 4 dot」讓每個人被綁在自己起點的 4-dot 晶格上，
  加上撞牆整段作廢。改成分段走法 + 撞牆反彈後是 12% / 1881 格。
  **這正是先做預覽鷹架才划算的地方** —— 這兩個數字接完整套才發現的話，
  修起來要動的東西多得多。

## 一、範圍

### 本期要做

1. **主機**：一台內網電腦跑廣場伺服器，所有人的 daemon 連到它
2. **進場**：帶「前線」的 vpet 進廣場；連不上就留在前線並提示
3. **場景鎖**：在廣場裡不能切到前線／營地，也不能做會改變角色的動作，直到離開

5. **聊天室**
6. **對戰邀請**：點別人的 vpet → 邀請 → 對方同意 → 開打（不記戰績）

| statusline／mod 顯示廣場 | 只做 daemon |

## 二、架構

```
 各人電腦                                   主機（KAIHSIANGCHANG）
┌──────────────────────────┐              ┌──────────────────────────┐
│ 瀏覽器（daemon 頁面）       │              │ 廣場伺服器 plaza-server.js  │
│      ↑↓ 既有的輪詢          │              │  - 在場名單（記憶體）        │
│ daemon ──────────────────┼── HTTP ─────→│  - 聊天（最近 50 則，記憶體）  │
│   （唯一連伺服器的人）       │←─ SSE 推播 ──┤  - 對戰邀請與結果             │
└──────────────────────────┘              └──────────────────────────┘
```

### 伺服器是獨立程式，不放在主機的 daemon 裡

主機自己也是玩家，會常常重開 daemon（改程式、更新）。伺服器若住在 daemon 裡，
主機每重開一次，全場的人都會被踢回前線。所以伺服器是**另一個 node 程式**，
在主機的 repo 裡用 `npm run plaza-host` 啟動（`src/daemon/plaza-server.js`），跟主機自己的 daemon 互不影響。
不做成 `vpet` 指令：部署樹裡沒有 `src/daemon/`，而且只有主機需要它。

- **零相依**：只用 node 內建的 `http`。上行用一般 POST，下行用 SSE（`text/event-stream`）。
  不引入 `ws` 套件 —— 這個 repo 目前沒有任何 npm 相依，安裝流程也沒有 `npm install`。
- **全部存在記憶體**：名單、聊天、邀請都不落地。伺服器重開 = 全場清空，大家回前線，
  可以接受（內網、小規模、沒有要保存的東西）。

### 為什麼是 daemon 連伺服器，不是瀏覽器直連

1. **單一寫入者**：daemon 是唯一能改 state 的人（「在廣場」、場景鎖、對戰結果都要寫 state）。
   瀏覽器直連的話，斷線回前線這件事就得由瀏覽器通知 daemon，多一個會漏的環節。
2. **關掉瀏覽器分頁不算離場**：vpet 繼續在廣場走，回來打開頁面還在。
3. 瀏覽器只跟本機 daemon 說話，不用處理跨網域。

### 位置仍然是決定性模擬

沿用第一版的核心設計：**伺服器不推進任何位置**，只發「起點」，每個 daemon 用同一個
純函數算出所有人的位置（§三）。伺服器只在進場、對戰結束這種「起點改變」的時候廣播。
好處是伺服器幾乎不用做事，也不需要逐拍同步。

一個人的走路由這組值決定，**全部由伺服器發**：

```json
{ "seed": 1739284, "fromStep": 9811230, "x": -16, "y": 20 }
```

- 進場：`x, y` 在畫面外某個邊界（見 §三「進場」），`fromStep` = 進場那一拍
- 對戰結束：`x, y` = 對戰時站的位置，`fromStep` = 結束那一拍，`seed` 換一個新的

第一版是「從 joinedAt 一路重播到現在」；改成「從最近一次的起點開始算」之後，
重播長度只到上一次對戰為止，順便解決了第一版「待越久重播越長」的問題。

### 時鐘同步

伺服器在每個 SSE 事件與每個 POST 回應都帶 `serverNow`，daemon 記下偏移：

```
clockSkew = serverNow - localNow
step      = floor((Date.now() + clockSkew) / STEP_MS)
```

內網延遲是毫秒級，一拍 750ms，誤差可忽略。

## 三、走路演算法

### 選定做法：任意斜率的「一段路」+ 增量快取

一次抽一段路（方向向量 + 長度），段內每拍走 1 dot，走完再抽下一段。

```
STEP_MS     = 750                  // 一拍多長（與家裡相同，定義在 core）
DIR_VECTORS = 分量 |v| <= 3 的互質向量，共 32 個（例如 1:0、3:1、2:3）
RUN_MIN/MAX = 6 ~ 34               // 一段路走幾拍（連續整數）
STAY_MIN/MAX= 4 ~ 8                // 停一次幾拍
STAY_CHANCE = 1/4                  // 抽中「停」的機率（換算成時間約 12%）

第 k 段：dir = DIR_VECTORS[hash(seed, 3k+1)]、len = hash(seed, 3k+2)
段內位置用 Bresenham 一次算出（主軸每拍 1 dot，副軸按比例四捨五入）
```

演算法改過兩次，兩次都是**看了畫面才發現問題**，這正是先做預覽鷹架的價值：

| 版本 | 做法 | 問題 | 一小時走訪 | 停留時間 |
|---|---|---|---|---|
| v1 | 每 4 拍走 4 dot，撞牆整段作廢 | 碎步磨蹭；貼邊的角色一直「決策了但沒動」像卡住，空轉還全被計進停留 | 486 格 | 37% |
| v2 | 一次抽一段路（上下左右 + 四斜向），撞牆反彈 | 範圍夠了，但**軌跡只有 8 種角度**，放久了整張圖是水平/垂直/45° 線疊出來的網格，像在走既定路線 | 1881 格 | 12% |
| v3 | 有理斜率（32 個互質向量）+ Bresenham，段長連續整數，走到牆邊就停、下一段重抽 | — | 1700 / 2673 格（64%） | 12.7% |

三個關鍵改動的理由：

**有理斜率。** v2「只有 8 種角度」是網格感的根因 —— 每段都是完美直線，疊久了必然
只剩那幾條線。改用互質向量（(3,1)、(2,3)…）配 Bresenham，角度從 8 種變 32 種。
**刻意不用 cos/sin 取連續角度**：那會引入超越函數，而 `Math.sin/cos` 的精確值不在
IEEE754 的保證範圍內（不同引擎可能差 1 ulp）。整個廣場的前提是每個 client 算出
**位元級相同**的結果，不能賭這個。互質向量 + Bresenham 全程整數。

**段長改成連續整數。** v2 的清單 `[4,6,8,12,16,20]` 全是偶數，導致每段終點永遠落在
同一個奇偶晶格上，轉彎點跟著規律化。

**撞牆從反彈改成「走到牆邊就停、下一段重抽方向」。** 固定方向的反彈會走出撞球檯般的
週期軌跡，反而強化單一感。順帶讓「最長段不得超過場地」這條隱形限制消失 ——
縮小場地不會再穿牆。（極端情況：已貼牆且朝外一步都走不了 → 掉頭走同一條線，
不當成「停」，否則貼牆很常見會把停留比例灌水到 21%。）

**停留時間佔比約 12%。** 注意「抽中停的機率」（1/4）與「站著的時間佔比」差很多 ——
一段路平均 15 拍、一次停平均 6 拍。**停下時角色仍持續演 IDLE_1/IDLE_2** ——
v1 停下時鎖 IDLE_1，連動畫都停掉，看起來像畫面當掉而不是站著休息。

- 位置從 `joinStep` 起一段一段累加，界限見 §五（頂/底其中一邊要留給名牌）
- 橫越 96 dot 寬的廣場約需 3~5 段 ≈ 70 秒，是刻意的慢步調

**一拍 750ms。** 家裡原本是 1000ms（被 statusline 最快 1 秒的刷新綁住），
2026-09 起全專案統一為 750ms，`STEP_MS` 只定義在 core 一處，廣場直接引用。
⚠️ `STEP_MS` 是**時間契約的一部分** —— 所有 client 都要用同一個值把牆鐘換成 step，
單邊改就等於改變別人眼中你的走路速度。前端輪詢刻意比一拍更密（`STEP_MS / 3`），
免得輪詢與拍子產生節拍差（同一拍畫兩次 / 跳過一拍）；合成 20 人約 0.3ms，可忽略。

> 這組數字**預期要微調**。先跑起來看畫面，再決定停留權重與速度。

### 為什麼可以用累加（而不是閉合公式）

累加需要從進場重播，看似 O(n)。實際算一下：待一小時 ≈ 3600 拍 ÷ 平均段長 15 ≈ **240 段**，每段幾個 hash。20 個人也才幾千次，一秒一次，可忽略。

而且 client 端**只在第一次計算時重播**，之後每拍只推進差量（快取 `{step, x, y}`）。重開視窗才會重播一次。

用整數格子累加，沒有浮點誤差累積的問題，任何 client 從任何時間點重播都得到完全一樣的結果。

### 為什麼不用「隨機路標 + 內插」

考慮過 `waypoint(k) = hash(seed,k)` 落點再內插的做法，它是 O(1) 且保證不出界，但：

- 兩個路標可能相隔整個廣場，內插會變成「等速滑行」，速度隨距離變動，不像走路
- 要讓速度固定就得讓停留時間正比於距離，那又變回累加

格子走位在像素風格下更自然（原版電子雞也是格子移動），且與現有「1 拍 1 步」的節奏一致。

### 面向

只有左右兩種（`getFacingRows` 是水平翻轉，沒有背面/正面幀）。

- `dir` 有水平分量（含斜向）→ 更新面向
- 純上 / 下 / 停 → **維持前一個面向**

這是美術限制。要真的有背面得補幀，不在本期。

⚠️ 轉身要等**真的邁出第一步**（段內第 1 拍）才生效。段的第 0 拍畫的其實是上一段的
終點、位置還沒動，那一拍就套新方向會讓角色在最後一步往右走的同時臉朝左，
每次轉向都閃一格反向。

### 第二版的兩個改動

**從任意起點出發。** 目前的走路函數假設起點由 `seed` 決定、在場內。改成吃
`{ seed, fromStep, x, y }`，從給定的點開始走。對戰結束後就是用這個從原地繼續走。

**進場：從邊界走進畫面。** 伺服器抽一個邊（上下左右）與邊上的位置，起點放在
**畫面外剛好一隻角色的距離**（例如左邊 = `x = -SPRITE`）。進場第一段**固定朝場內走**，
長度至少走到完全進入畫面（`SPRITE` 拍以上），之後才回到一般的隨機抽段。
「畫面外」只在進場那一段允許，之後的界限照常是場內。

**不分區。** 營地有分區（每隻只在自己那塊走），廣場沒有，所有人共用整個場地的界限。

## 四、協定

伺服器預設 port `37373`。所有回應都帶 `serverNow`。

### 上行（daemon → 伺服器，POST JSON）

| 路徑 | body | 說明 |
|---|---|---|
| `/join` | `{ name, char, stage, card }` | 進場。回傳 `{ id, roster, chat, serverNow }`；`id` 是這次連線的代號 |
| `/leave` | `{ id }` | 離場 |
| `/chat` | `{ id, text }` | 發言 |
| `/invite` | `{ id, to }` | 邀請對戰 |
| `/answer` | `{ id, inviteId, accept }` | 回覆邀請 |

`card` 沿用幽靈對戰的戰卡格式（`myCard()`：`character / power / train / stage`），對戰時用。

### 下行（伺服器 → daemon，SSE `GET /events?id=…`）

| 事件 | 內容 |
|---|---|
| `enter` | 有人進場：`{ id, name, char, stage, walk }` |
| `leave` | 有人離場：`{ id }` |
| `chat` | `{ id, name, text, at }` |
| `invite` | 有人邀請我：`{ inviteId, from }` |
| `invite-closed` | 邀請結束（拒絕／逾時／對方離場）：`{ inviteId, reason }` |
| `battle` | 對戰開始：`{ a, b, winner, seed }`（全場都會收到，旁觀的人用來把兩隻停住） |
| `walk` | 某人的走路起點改了（對戰結束）：`{ id, walk }` |
| `ping` | 每 15 秒一次，讓兩邊都知道連線還活著 |

**連線就是在場**：SSE 斷掉超過 **10 秒**沒接回來，伺服器就把這個人移出名單並廣播 `leave`。
那 10 秒是給短暫的網路抖動，不是給重開 daemon 用的 —— 重開 daemon 就是離場。

### 身分

名牌沿用現有的 `code`（`vpet code <名字>` 設定；沒設過會自動產生）。
同名的人進場時，**後進的取代先進的**（同一個人開了兩個 daemon 也是這樣處理）。

## 五、渲染

### 舞台

單位換算：1 個 cell = 1 dot 寬 × 2 dot 高；1 dot 在畫面上是 8 × 8 px 的正方形。
所以**視覺上的正方形 = dot 數相等**，不是 cell 數相等。

| | 現況（家裡） | 廣場 |
|---|---|---|
| dot | 52 × 16 | **96 × 48**（2:1） |
| cell | 52 欄 × 8 列 | 96 欄 × 24 列 |
| 畫面 | 416 × 128 px | **768 × 384 px** |

原本定 96×96 正方形（768×768），實際看過之後分兩次改矮到 48 —— 瀏覽器裡連表頭都要
捲動才看得完。注意「視覺正方形」是 **dot 數**相等而不是 cell 數相等
（1 cell = 1 dot 寬 × 2 dot 高），這點很容易搞錯。

改場地只要動 `plaza-walk.js` 的 `PLAZA_W` / `PLAZA_H`，其餘（合成、名牌位置、
畫布尺寸、測試）全部從那裡推導。

**可走範圍不等於場地**：底部要保留一個 cell 列（`LABEL_RESERVE`）給名牌，
所以 `y ∈ [0, PLAZA_H - SPRITE - 2]`。沒有這段保留區的話，角色走到最底時腳下那一列
已經在畫面外，名牌會整個消失。

`#stage` 目前是 `width:fit-content` + `min-width:416px`（見 `daemon.js` 該段註解），
廣場模式要能撐到 768 px。

### y 排序合成器（本期最大的一塊新程式）

現有 `renderCells` 是把一排排 cell 攤平輸出，沒有「把 sprite 貼到 (x,y)」的概念。需要新增：

1. 建一張 `plazaW × plazaH` 的空 cell 緩衝
2. 把所有 vpet 依 **y 由小到大**排序（y 大的後畫 → 蓋在前面，painter's algorithm）
3. 逐一貼上（含名牌）
4. 交給既有的 `renderCells` 輸出

### 名牌

角色腳下顯示 `code`。PvP 已有「腳下名牌」的先例（`2799390 PvP 強化：固定練習對手、雙方腳下名牌`），沿用同一套。

名牌走**文字層**（整張圖渲染成 ANSI 之後才貼字），因為名牌要支援中文，一個字佔
一整個 cell，沒有 dot 級字模。代價是它不在 painter's algorithm 裡，預設會浮在所有人
身上 —— 後排的名字蓋在前排的身體上，前後關係整個看反。

**解法：合成時多維護一張「這個 dot 是誰畫的」緩衝**（`owner`），名牌要佔的那幾格若
被 z 較大（站得比較前面）的人畫過，整條名牌就不顯示。切一半更難看，所以是整條省略。
同一列多人重疊時也改成保留前排那個，與遮擋規則一致。

實測名牌顯示率：5 人 91%、12 人 66%、20 人 50%。人多時掉得明顯，
若之後覺得不能接受，下一步是「腳下被擋就改標在頭上」。

### 對手角色本機沒安裝

**已經解決過**：PvP 的黑影 fallback（`91ce825`）。廣場直接沿用 —— 讀不到角色資產就用 Shadow 剪影，不要拒絕顯示。

### statusline 不顯示廣場

狀態列只有一行，二維矩形不可能塞下。**廣場是 daemon 專屬功能**，statusline 使用者只會看到「外出中」文字，想看廣場要開獨立視窗。這點需要在文件寫清楚。

## 六、進場、離場與場景鎖

### 入口

只在 daemon 頁面：**前線畫面**多一個「廣場」按鈕（與營地切換並列）。
statusline、mod、CLI 都不提供入口（本期只做 daemon）。

### 進場

1. 按「廣場」→ daemon 帶前線那隻 `POST /join`
2. 成功 → 頁面切到廣場畫面，自己的 vpet 從邊界走進來
3. 失敗（主機沒開、不在內網、名單滿）→ **留在前線**，頁面顯示原因，例如
   「連不上廣場（主機沒開，或你不在公司內網）」

進場前的擋法：進化演出中、對戰中、睡覺中不能進場（與「進化演出中不能切營地」同一套防呆）。

### 在廣場時鎖住什麼

| 項目 | 在廣場時 | 理由 |
|---|---|---|
| 切到前線／營地 | **擋下**，只能按「離開廣場」 | 規格第 3 點 |
| 訓練值成長、自動戰鬥、進化判定 | **暫停** | 人不在家 |
| 摸摸、閒置睡眠 | **暫停** | 同上 |
| CLI 的 `battle` / `evolve` / `reset` / `jogress` / `swap` / `release` / `keep` | **擋下**，提示「在廣場中，先離開」 | 會改變前線的角色 |
| `card` / `tree` / `album` / `stats` 等純資訊 | 照常 | 與場景無關 |

⚠️ hook 仍照常寫 `hook.json`，但在廣場期間不得拿它加訓練值、不得武裝自動戰鬥。

### 「在廣場」存在哪

`state.plaza = { id, at }`，daemon 每拍寫一次。**state 那份只是給
statusline / CLI 看的**（顯示「在廣場」、擋指令），不代表持久在場：

- daemon 啟動時看到 `state.plaza` → 第一拍就清掉、回前線（上次沒正常離場）
- CLI 看 `at`：超過 10 秒沒更新（daemon 已經死了）就當作不在廣場，殘留不會永遠鎖住指令
- 斷線重試失敗 → 清掉、回前線，頁面提示「與廣場的連線中斷，已回到前線」

### 離場

- 按「離開廣場」→ `POST /leave` → 回前線
- 關掉 daemon → 盡力送 `/leave`；送不到也沒關係，伺服器 10 秒後自己清
- 關掉瀏覽器分頁 → **不算離場**，vpet 繼續在廣場

## 七、聊天

### 畫面

- 廣場畫面下方一個聊天框：訊息列表 + 輸入列
- 說話的人頭上冒一個**短泡泡**（前 12 字，顯示 5 秒）；前端畫在角色畫布上，撞到右上角的日期／天氣看板就改放到名牌下面

### 規則

| 項目 | 值 |
|---|---|
| 一則字數上限 | 100 字 |
| 發言頻率 | 每人每秒最多 1 則（伺服器擋） |
| 保留 | 伺服器記憶體裡最近 **50** 則，進場時一併發給你 |
| 落地 | **不存檔**。伺服器重開就清空 |
| 系統訊息 | 「XX 進入廣場」「XX 離開了」「XX 改名為 YY」（同名取代不報）；對戰的「XX 對 YY 發起對戰」留到第 3 期 |

內網、熟人之間使用，本期不做刪訊息、禁言。主機要清空聊天的話重開伺服器即可。

## 八、對戰

### 流程

1. 點別人的 vpet → 選單「⚔ 邀請對戰」；對方畫面下方出現邀請列（接受／拒絕＋倒數）
2. 對方頁面跳出「XX 邀請你對戰」：同意／拒絕，**30 秒**沒回就當拒絕
3. 同意 → 伺服器決定勝負、廣播 `battle`
4. 兩邊各自播對戰演出 → 結束後回到廣場，從原地繼續走（伺服器發新的 `walk`）

同一時間一個人只能有一個進行中的邀請或對戰；對戰中的人不能被邀請。

### 誰決定勝負

**伺服器決定**，用跟現在對戰相同的勝率公式（雙方戰卡的 `power / train / stage`）加
伺服器抽的亂數。兩邊收到同一個 `winner`，播出來的結果一定一致。
不讓 client 各自算，是因為兩台的 state 可能不同步，各算各的會出現「兩邊都贏」。

### 演出

- 對戰的兩人：**疊一層在廣場上面**，不換畫面。廣場壓暗，中間疊一塊前線大小的
  戰鬥演出（沿用前線既有的對戰畫面與雙方腳下名牌，等同幽靈對戰現在的
  `forceBattleEnemy / forceBattleWin / pvpOppLabel`），演完淡出，廣場在後面照常進行。
  不整個換成前線畫面的理由：廣場是營地那套小格子（6px），戰鬥是前線的大格子（8px），
  整個換掉畫布大小會跳；疊層則兩邊各用各的格子，互不影響（2026-10-07 定案）
- 旁觀的人：兩隻停在原地，頭上顯示 ⚔，結束後繼續走
- **不記戰績**：沿用 `battleNoCount`，勝負不影響戰績、勝率與進化條件
- **不留痕跡**：前線戰鬥演完會把心情歸 0、記下「上一場敵人」—— 廣場對戰開演前先記下這兩個，演完還原
- **演出長度**：伺服器讓兩隻停 18 秒（前線戰鬥最長 21 拍 × 750ms ≈ 15.8 秒，再留一點延遲）；
  期間不能移動，打完照原本的自動／手動恢復
- **戰力**：daemon 進場時算好 `min(基礎 + 訓練值, 階級上限)` 一起送（跟幽靈對戰同一套），
  伺服器用 `50 + 戰力差 %`（夾 5～95%）擲骰

## 九、失敗與邊界

| 情況 | 行為 |
|---|---|
| 主機沒開／不在內網 | 進場失敗，留在前線並提示原因 |
| 在廣場時伺服器掛掉 | SSE 斷線 → 重試 10 秒 → 失敗就回前線並提示 |
| 名單滿 | 上限 **20 人**，提示「廣場人太多了，晚點再來」 |
| 同名 | 後進的取代先進的，先進的那個 daemon 收到 `leave` 後回前線並提示「你在別處進入了廣場」 |
| 邀請中對方離場 | 邀請作廢，`invite-closed` 帶 `reason: 'left'` |
| 對戰中自己斷線 | 對方照常播完；斷線的人回前線，這場不記（本來就不記） |
| 對方角色本機沒安裝 | 用黑影 fallback（沿用 PvP 的做法） |

## 十、主機與連線設定

### 使用者：不用設定

廣場伺服器的位址**內建在 release 裡**：`http://192.168.164.46:37373`（主機 `KAIHSIANGCHANG` 的 IP）。

   要看伺服器的輸出時改用終端機跑 `npm run plaza-host`

### 舊的幽靈對戰：隱藏

|---|---|

## 十一、安全

- 只在內網開放；防火牆規則限定私人／網域設定檔
- 不做驗證：內網、熟人使用。代價是內網裡任何人都能連上、能冒用別人的名牌。
  要開放外網時一定要補驗證（另案）
- 送到伺服器的只有：名牌、角色 id、階級、戰卡數值、聊天文字。**不含**本機路徑、token 用量、花費
- 伺服器對所有輸入做長度與格式檢查（名牌沿用 `validId`、聊天 100 字），不信任 client
