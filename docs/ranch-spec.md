## 一、這是什麼

`reset` 目前是純粹的犧牲：把養到頂的桌寵丟掉，重抽一隻。這是整個養成循環最大的
摩擦 —— 玩家因此不想探索別的進化路線，因為代價是「失去現在這隻」。

牧場把 `reset` 從損失變成收成：舊的不會消失，而是**活著**待在一個屬於你的空間裡，
隨時可以叫回來。蒐集本身成為玩下去的理由。

### 心智模型：冰箱

> **同時只有一隻現役。現役會成長，牧場裡的全部凍結。**

不是墓園（收進去就回不來），也不是隊伍（多隻同時活動）。是冰箱：拿出來的那隻在
過生活，冰箱裡的維持原樣，什麼時候換都可以。

「同時只養一隻」這個前提沒有被破壞 —— 只是「另一隻」從被刪掉變成被保存。

### 為什麼先做牧場、後做廣場

原本的計畫是先做共用廣場。改成先做牧場，理由由重到輕：

1. **牧場不需要任何後端。** 廣場規格裡的 seed 由伺服器發、時鐘校正、在場名單、
   `MAX_STAY` 幽靈清理、20 人上限 —— 那些全部是為了「多個 client 算出同一畫面」
   而存在的。牧場只有一個 client，全部不需要。
2. **做完之後，共用廣場只剩「把名單來源從本機檔案換成 Worker」。** 畫面層、走路、
   y 排序、名牌全部共用。最難的部分被縮到最小。
3. **中途停掉也還有一個完整功能。** 若共用廣場最後因為維運成本不做，牧場仍然成立。
4. **它同時救了圖鑑。** 圖鑑是靜態格子圖；同一批資料改成「一座住著你養過的怪的
   院子」，吸引力差很多。

### 本期不做

| 項目 | 為什麼延後 |
|---|---|
| 暱稱 | 蒐集玩法沒有名字就沒有感情，但不影響核心，排第二版 |
| 上限擴充（圖鑑收集度解鎖之類） | 先把上限寫成一個常數，之後再談怎麼長 |
| 牧場內的互動（餵食、對戰邀請） | 等基礎穩定 |
| 牧場成員之間的關係 | 同上 |

## 二、資料模型

### 存哪裡

`~/.claude/agumon-statusline/state/ranch.json`，與 `album.json` 同層。

```json
{
  "v": 1,
  "cap": 8,
  "pets": [
    {
      "id": "r7k2m",
      "keptAt": 1787000000000,
      "state": { "characterId": "wargreymon", "trainingBonus": 37, ... }
    }
  ]
}
```

- `id`：短亂數字串。**不能用 characterId 當識別** —— 一直 reset 會有好幾隻 agumon，
  牠們是不同個體。
- `keptAt`：收進來的時間，用於排序與顯示。
- `state`：**整包桌寵狀態**，見下。

### `state` 要存什麼 —— 本規格最重要的一段

交換必須連狀態一起搬。現有的換角色路徑（`applyForceFlags` 的 `force.character`
分支）會清掉 `trainingBonus`、`battleTotalCount/WinCount`、`tagStats`、`stats`、
`lifeStats`、`mood`、`inheritedPower`，並重設 `birthAt` / `lastEvolveAt`。

> ⚠️ **牧場交換絕對不能走那條路徑。** 走錯的話，玩家把 WarGreymon 拿回來會發現
> 訓練值 0、勝率歸零、出生時間變成今天。而且**不會有任何錯誤訊息** ——
> 只是他幾十小時的心血無聲消失。這是這個功能最容易做壞、也最不可挽回的地方。

做法：**存整包 state，扣掉一份明確列出的「暫態欄位」黑名單。**

不用白名單，是因為兩種漏掉的後果差很多：
- 白名單漏掉一個成長欄位 → 玩家的進度永久消失，救不回來
- 黑名單漏掉一個暫態欄位 → 還原出一個過期的動畫狀態，下一拍就自我修正

所以判準是「**不確定就不要加進黑名單**」。

暫態欄位（動畫 / 視窗，收進去時丟掉）：

```
exprStartStep  roarStartStep  happyStartStep  lastStepSeen
battleStartStep  evoStartStep  cardStartStep  dropStartStep
walkPhaseOffset  lastPos  lastFacing
lastBattleTriggerTs  lastEvolveTriggerTs  lastDropTriggerTs  lastPetTriggerTs  lastCardTriggerTs
_albumLast  _force*  _pvp*
```

其餘一律保存，包含（列出來是為了說明「這些都不能掉」，不是完整清單）：
`characterId`、`trainingBonus`、`inheritedPower`、`birthAt`、`lastEvolveAt`、
`battleTotalCount`、`battleWinCount`、`tagStats`、`stats`、`lifeStats`、`mood`、
`evoHistory`（`vpet tree` 靠它）、`_evo_*` 條件 latch、`_r5hPeaked`、`_costEvolved`、
`_evoSpendBySession`。

### 上限

**8 隻**（`RANCH_CAP`）。

理由不是技術而是兩件事：院子沿用廣場的 96×48 舞台（24 個角色位），要看得清楚誰是誰
就不能塞滿；更重要的是**上限要小到讓「放掉哪一隻」是個真的決定**，太大就沒有取捨。

滿了的處理：**明確拒絕，要玩家自己 `release`**。不自動淘汰最舊的 —— 靜默刪掉別人
養的東西是不能做的事。

## 三、操作

### 四個動作

| 動作 | 效果 | 牧場數量 |
|---|---|---|
| **keep** | 現役收進牧場 → **重抽一隻新的 starter**（＝保留版 reset） | +1 |
| **swap** | 現役收進牧場，把指定那隻叫出來 | 不變 |
| **release** | 把牧場裡指定那隻放生（永久刪除） | −1 |
| **list** | 看牧場內容 | 不變 |

`reset` **維持原意**（丟掉重抽，不留）。它和 `keep` 形成一組對照：這隻要不要留，
玩家自己決定。

滿了的時候：`keep` 拒絕（要先 `release`），`swap` 照常（一進一出，數量不變）。

### CLI

```
vpet ranch                   列出牧場（編號 / 角色 / 階級 / 戰力 / 收進時間）
vpet keep                    現役收進牧場 + 抽一隻新的
vpet swap <編號|名稱>         現役收進牧場，叫出指定那隻
vpet release <編號|名稱>      放生（永久刪除，要二次確認）
```

**識別**：`<編號>` 是權威（`vpet ranch` 列出來的序號）。名稱只在牧場裡該角色唯一時
才能用，重複時要求改用編號 —— 不要猜。

CLI 視角就是冰箱：收進 / 拿出 / 列清單。**互動（看牠們散步、點牠、摸牠）是 daemon
專屬** —— 狀態列只有一行，塞不下一座院子，這與廣場的結論一致。

### daemon

以上四個動作各對應一個 UI 按鈕，加上「院子」畫面本身。放進既有的指令面板
（`UI_BUTTONS` / `UI_FORMS`），`release` 要走確認流程（比照 `reset`）。

## 四、院子畫面

**直接沿用廣場的合成器**（`src/daemon/plaza.js`）與走路演算法
（`src/shared/plaza-walk.js`），一行都不用改：

- 舞台 96×48 dot（768×384 px）
- y 排序、名牌固定在腳下、逐字遮擋
- 牧場成員 = `occupants`，`code` 填角色顯示名（不是玩家名牌）
- **NPC 關掉**（`opts.npc = false`）—— 院子裡不該有野生 vpet 亂入，
  這個開關就是為此預留的

差異只有名單來源：廣場是伺服器發的在場名單，院子是本機 `ranch.json`。

**seed 從哪來**：每隻的 `id` 雜湊成 seed。不需要伺服器分配（那是廣場為了跨 client
一致才需要的），本機自己算就好，而且同一隻每次開院子的走位都一樣。

現役那隻要不要也出現在院子裡？**要**，而且要標示得出來（沿用「自己 = 亮黃名牌」）。
不然院子會看起來像少了一隻。

## 五、進化條件掛牧場

讓蒐集回頭餵養成。新增三個條件型別：

| 型別 | 意思 |
|---|---|
| `ranch_count` | 牧場裡有 N 隻以上 |
| `ranch_has` | 牧場裡有特定角色 / 特定 stage / 特定 tag |
| `ranch_species` | **不重複**的種類數達 N（獎勵蒐集廣度，不是數量） |

三個必須處理的問題：

**1. `evalCondition` 要多吃一個參數。** 現有條件全部只讀 `st`（現役那一隻的狀態）
與 `input`；牧場條件要讀另一個檔案。這會同時動到 `agumon-core.js` 和進化路線編輯器
（`src/editor/route_editor_server.js` + `src/shared/evo-rules.js`），不是加一個
`case` 就好。

**2. 一律 latch（達成過就算數）。** 現有條件裡 `power_at_least` / `win_rate` 是即時的
（所見即所得），`r5h_peak` / `cost_threshold` 是 latch 的。牧場條件如果做成即時，
玩家把那隻換出來就會失去資格，會遇到「剛剛明明可以進化」。latch 沒有這個問題。

**3. 只能用在後段分支或彩蛋線，絕對不能擋主線。** 新玩家的牧場是空的，任何掛牧場的
條件在他退休第一隻之前都走不到。另外進化路線編輯器有死路分析，它得認得這些新型別，
否則會把整條線誤報成死路。

## 六、與既有系統的交互

### PvP

**戰卡永遠是「當前取出的那隻」**，要用誰是玩家的自由。

⚠️ 因此 **`swap` / `keep` 之後必須重新上傳戰卡**。漏掉的話你的幽靈會停在舊角色，
別人挑戰到的是一個你已經收進冰箱的分身。

這確實讓玩家可以「停一隻滿等的、養新的、打 PvP 前換回來」。這是刻意接受的 ——
本作偏單機蒐集，養每一隻的時間成本是真的。

### 圖鑑

`album.json` 記的是「你養過誰」（角色 id → 首次取得時間），與牧場是不同維度：
圖鑑是**種類**的紀錄，牧場是**個體**的收藏。兩者並存，不合併。

`keep` / `release` 都不影響圖鑑 —— 放生了也還是養過。

### reset

不變。`reset` 丟掉重抽，`keep` 保留重抽。

### hook / 成長

牧場裡的凍結，代表 hook 的訓練值、自動戰鬥、活動時戳**只作用在現役那一隻**。
這是自然結果（那些都寫在 `state` 的現役欄位上），不需要額外的 gate ——
與廣場「不在家要暫停飼育」不同，那邊才需要特別擋。

### 多視窗 / daemon 當家

`ranch.json` 的寫入時機只有 keep / swap / release 三個明確動作，不在每秒 tick 上，
所以沒有多視窗競寫的問題。但**交換會同時改 `ranch.json` 與 `color-state.json`**，
兩個檔要一起換 —— 中途失敗會導致同一隻同時在冰箱裡和手上（或兩邊都沒有）。
用既有的 `atomicWrite`，並且**先寫 ranch 再寫 state**：這個順序下最壞的結果是
「牧場多一份、現役沒換成」，玩家看得到也救得回；反過來則是桌寵消失。

## 七、失敗與邊界

| 情況 | 行為 |
|---|---|
| 牧場已滿時 `keep` | 拒絕並提示先 `release`，不自動淘汰 |
| `swap` 指定的編號不存在 | 列出目前牧場內容，不做任何事 |
| 名稱重複（三隻 agumon）| 要求改用編號，不要猜 |
| `ranch.json` 損毀 / 讀不到 | 視為空牧場並保留原檔（改名備份），不要覆寫 —— 那是玩家的收藏 |
| 牧場裡的角色本機沒有美術 | 沿用 PvP 的黑影 fallback（合成器已經有） |
| `release` | 二次確認。這是唯一不可逆的動作 |
| 舊版 state 沒有某些欄位 | 還原時缺欄位就用預設值，不要因此拒絕還原 |
