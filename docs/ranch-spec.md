### 實作後發現、規格沒寫到的

- **force 的新鮮度下界不能是 0。** 其他 force 指令都用 `age >= 0 && age < 窗口`
  判斷是否過期。CLI 與當家端是不同 process，系統時鐘微調（NTP、休眠喚醒）就足以讓
  時戳看起來「來自未來」，指令會無聲消失而使用者只看到「打了沒反應」。
  牧場這邊改成 `age >= -5000`。
- **`restorePet` 必須先刪再套，不能只做 `Object.assign`。** 舊角色有、新角色沒有的
  欄位（`inheritedPower`、某個 `_evo_*` latch）會殘留，變成兩隻寵物的狀態混在一起。
  這種 bug 只在特定組合下顯現，很難查。
- **swap 之後要換新 id。** 收進去的那份若沿用被取出那份的 id，兩者會撞號。
- **表演中要擋下牧場操作**（戰鬥 / 進化 / 空降）。交換會把 `st` 整包換掉，
  正在播的戰鬥會接到不存在的對手。
- **`joinStep` 不能隨便填 0。** 院子第一版把它寫死成 0，但餵進去的 step 是牆鐘算的
  （約 24 億），`posAt` 於是要跑一億多次**同步**迴圈 —— 整個 daemon 的 event loop
  卡死，連無關的 `/state` 都一起停擺。已在 `plaza-walk.js` 加 `MAX_REPLAY` 上限：
  呼叫端傳錯參數不該讓伺服器當掉。院子改用「這次 daemon 啟動的時間」當基準。
- **院子的 canvas 不能吃 `max-width:100%`。** 96 欄 = 768px 比家裡的 52 欄寬，
  窄視窗會把它縮成非整數倍，像素風糊掉（家裡為了地平線對齊已經踩過一次）。
  改成寧可讓 `#petbox` 裁掉右邊。

## 一、這是什麼

`reset` 目前是純粹的犧牲：把養到頂的桌寵丟掉，重抽一隻。這是整個養成循環最大的
摩擦 —— 玩家因此不想探索別的進化路線，因為代價是「失去現在這隻」。

牧場把 `reset` 從損失變成收成：舊的不會消失，而是**活著**待在一個屬於你的空間裡，
隨時可以叫回來。蒐集本身成為玩下去的理由。

### 心智模型：冰箱

> **同時只有一隻現役。現役會成長，牧場裡的全部凍結。**

不是墓園（收進去就回不來），也不是隊伍（多隻同時活動）。是冰箱：拿出來的那隻在
過生活，冰箱裡的維持原樣，什麼時候換都可以。

「同時只養一隻」這個前提沒有被破壞 —— 只是「另一隻」從被刪掉變成被保存。

### 為什麼先做牧場、後做廣場

原本的計畫是先做共用廣場。改成先做牧場，理由由重到輕：

1. **牧場不需要任何後端。** 廣場規格裡的 seed 由伺服器發、時鐘校正、在場名單、
   `MAX_STAY` 幽靈清理、20 人上限 —— 那些全部是為了「多個 client 算出同一畫面」
   而存在的。牧場只有一個 client，全部不需要。
2. **做完之後，共用廣場只剩「把名單來源從本機檔案換成 Worker」。** 畫面層、走路、
   y 排序、名牌全部共用。最難的部分被縮到最小。
3. **中途停掉也還有一個完整功能。** 若共用廣場最後因為維運成本不做，牧場仍然成立。
4. **它同時救了圖鑑。** 圖鑑是靜態格子圖；同一批資料改成「一座住著你養過的怪的
   院子」，吸引力差很多。

### 本期不做

| 項目 | 為什麼延後 |
|---|---|
| 暱稱 | 蒐集玩法沒有名字就沒有感情，但不影響核心，排第二版 |
| 上限擴充（圖鑑收集度解鎖之類） | 先把上限寫成一個常數，之後再談怎麼長 |
| 牧場內的互動（餵食、對戰邀請） | 等基礎穩定 |
| 牧場成員之間的關係 | 同上 |

## 二、資料模型

### 存哪裡

`~/.claude/agumon-statusline/state/ranch.json`，與 `album.json` 同層。

```json
{
  "v": 1,
  "cap": 8,
  "pets": [
    {
      "id": "r7k2m",
      "keptAt": 1787000000000,
      "state": { "characterId": "wargreymon", "trainingBonus": 37, ... }
    }
  ]
}
```

- `id`：短亂數字串。**不能用 characterId 當識別** —— 一直 reset 會有好幾隻 agumon，
  牠們是不同個體。
- `keptAt`：收進來的時間，用於排序與顯示。
- `state`：**整包桌寵狀態**，見下。

### `state` 要存什麼 —— 本規格最重要的一段

交換必須連狀態一起搬。現有的換角色路徑（`applyForceFlags` 的 `force.character`
分支）會清掉 `trainingBonus`、`battleTotalCount/WinCount`、`tagStats`、`stats`、
`lifeStats`、`mood`、`inheritedPower`，並重設 `birthAt` / `lastEvolveAt`。

> ⚠️ **牧場交換絕對不能走那條路徑。** 走錯的話，玩家把 WarGreymon 拿回來會發現
> 訓練值 0、勝率歸零、出生時間變成今天。而且**不會有任何錯誤訊息** ——
> 只是他幾十小時的心血無聲消失。這是這個功能最容易做壞、也最不可挽回的地方。

做法：**存整包 state，扣掉一份明確列出的「暫態欄位」黑名單。**

不用白名單，是因為兩種漏掉的後果差很多：
- 白名單漏掉一個成長欄位 → 玩家的進度永久消失，救不回來
- 黑名單漏掉一個暫態欄位 → 還原出一個過期的動畫狀態，下一拍就自我修正

所以判準是「**不確定就不要加進黑名單**」。

暫態欄位（動畫 / 視窗，收進去時丟掉）：

```
exprStartStep  roarStartStep  happyStartStep  lastStepSeen
battleStartStep  evoStartStep  cardStartStep  dropStartStep
walkPhaseOffset  lastPos  lastFacing
lastBattleTriggerTs  lastEvolveTriggerTs  lastDropTriggerTs  lastPetTriggerTs  lastCardTriggerTs
_albumLast  _force*  _pvp*
```

其餘一律保存，包含（列出來是為了說明「這些都不能掉」，不是完整清單）：
`characterId`、`trainingBonus`、`inheritedPower`、`birthAt`、`lastEvolveAt`、
`battleTotalCount`、`battleWinCount`、`tagStats`、`stats`、`lifeStats`、`mood`、
`evoHistory`（`vpet tree` 靠它）、`_evo_*` 條件 latch、`_r5hPeaked`、`_costEvolved`、
`_evoSpendBySession`。

### 上限

**3 隻**（`RANCH_CAP`）。8 → 5 → 3，兩次都是實際看過畫面之後往下調。

⚠️ 調小時既有玩家可能**已經超過新上限**（例如 5 隻遇到上限 3）。`loadRanch` 刻意
**不截斷** —— 少一隻就是永久少一隻，寧可讓數字顯示成 `5/3` 也不能自己動手刪。
超過的狀態下 `keep` 會被拒絕，玩家用 `release` / `swap` 自己收斂回來。

⚠️ **上限是產品設定，不吃存檔。** 第一版把 `cap` 寫進 `ranch.json` 了，那會讓「改常數」
對既有玩家完全無效 —— 而且是最難聯想的那種 bug：程式改了、測試也綠，就只有自己那台
沒變。現在 `loadRanch()` 會把讀到的 `cap` 直接丟掉（下次存檔就消失），
一律以 `ranchCap()` 為準。日後真要做「牧場擴充」，加一個 `capBonus`，不要復活這個欄位。

超過上限不會刪東西 —— 上限只在 `keep` 時擋。手上已經比新上限多的人，
維持現狀直到自己 `release` 或 `swap` 出去。

理由不是技術而是兩件事：院子沿用廣場的 96×48 舞台（24 個角色位），要看得清楚誰是誰
就不能塞滿；更重要的是**上限要小到讓「放掉哪一隻」是個真的決定**，太大就沒有取捨。

滿了的處理：**明確拒絕，要玩家自己 `release`**。不自動淘汰最舊的 —— 靜默刪掉別人
養的東西是不能做的事。

## 三、操作

### 四個動作

入口按鈕叫 **🐮 牧場 / ⚔ 前線**，不是「院子 / 回家」——「家」在這裡有兩個意思會打架：
廣場那邊的「回家」是從廣場回到自己的舞台，牧場這邊按了是回到現役那隻。
用「前線」指現役、「牧場」指收藏就不會混。

| 動作 | 效果 | 牧場數量 |
|---|---|---|
| **keep** | 現役收進牧場 → **重抽一隻新的 starter**（＝保留版 reset） | +1 |
| **swap** | 現役收進牧場，把指定那隻叫出來 | 不變 |
| **release** | 把牧場裡指定那隻放生（永久刪除） | −1 |
| **list** | 看牧場內容 | 不變 |

`reset` **維持原意**（丟掉重抽，不留）。它和 `keep` 形成一組對照：這隻要不要留，
玩家自己決定。

滿了的時候：`keep` 拒絕（要先 `release`），`swap` 照常（一進一出，數量不變）。

### CLI

```
vpet ranch                   列出牧場（編號 / 角色 / 階級 / 戰力 / 收進時間）
vpet keep                    現役收進牧場 + 抽一隻新的
vpet swap <編號|名稱>         現役收進牧場，叫出指定那隻
vpet release <編號|名稱>      放生（永久刪除，要二次確認）
```

**識別**：`<編號>` 是權威（`vpet ranch` 列出來的序號）。名稱只在牧場裡該角色唯一時
才能用，重複時要求改用編號 —— 不要猜。

CLI 視角就是冰箱：收進 / 拿出 / 列清單。**互動（看牠們散步、點牠、摸牠）是 daemon
專屬** —— 狀態列只有一行，塞不下一座院子，這與廣場的結論一致。

### daemon

以上四個動作各對應一個 UI 按鈕，加上「院子」畫面本身。放進既有的指令面板
（`UI_BUTTONS` / `UI_FORMS`），`release` 要走確認流程（比照 `reset`）。

## 四、院子畫面

**直接沿用廣場的合成器**（`src/daemon/plaza.js`）與走路演算法
（`src/shared/plaza-walk.js`）：

- 舞台 **52×40 dot（416×320 px）**。寬度刻意對齊家裡（前線）的舞台 ——
  兩個畫面在同一個版位切換，寬度一樣才不會每按一次按鈕整頁就跳一下。
  廣場與院子仍是**不同的空間**（廣場 96×48，要塞 20 個人），
  所以場地從模組常數改成傳進來的 `field` 物件（`makeField(w, h)`），
  `minX/maxY` 這些由它推導（要扣角色寬高、扣名牌保留區）——
  讓呼叫端自己算遲早有人算錯一格，而症狀是「偶爾有隻角色被裁掉半個身體」這種
  很難聯想到原因的東西。

  ⚠️ **52×40 對 8 隻來說很擠**：可站位置只有 37×25，而角色是 16×16，
  100% 的時間至少有兩隻重疊。（上限後來調成 5，擁擠程度跟著緩解，場地尺寸沒動。）這是刻意先試小的（尺寸換版面一致），不是算錯 ——
  覺得太擠就把 `YARD_FIELD` 調大，那是一行的事。尺寸走過 96×48 → 128×80 → 52×40。

### 右鍵選單

在角色身上按右鍵 → 標頭顯示名字 / 階級 / 戰力 / 勝率 / 收進來的時間，
下面兩個動作：換出來、放生。名牌拿掉之後，這是辨識「誰是誰」的唯一途徑，
所以資訊全部塞在標頭，右鍵一按就看完。

⚠️ 曾經有第三個動作「名片」，把同一份資料倒進畫布下方的 `#cmdout`。**已移除**：
牧場的畫布是滿尺寸（`max-width:none`）、外層 `#petbox` 會捲動，輸出區常常落在
看不到的位置，按了像沒反應。資訊本來就該在標頭，多一顆鈕只是多一條會壞的路。

命中判定放**前端**、用最後一次 `/yard` 回來的座標算。不另開 `/yard/hit` 端點是因為
位置每拍都在動 —— 點下去再問伺服器，回來時已經是下一拍的位置，會抓錯人。
由後往前找（畫在最上層的優先），跟眼睛看到的一致。

送指令時用**內部 id 而不是編號**：編號會隨清單增減位移，「選單畫出來的當下是 #3，
送出時已經變成別人」是很實際的風險。CLI 的 `resolve()` 因此也接受 id。

### 牧場的摸摸：有反應，但**不動心情值**

家裡點角色 = 摸摸（會加心情）。牧場也能摸，但那是**純表演** —— 只換一幀表情，
心情值不動、`ranch.json` 一個位元組都不寫。牧場是冰箱，裡面的東西不會因為你戳牠
而變好或變壞。

走了兩版：一開始整個關掉（畫布上那幾隻都是收起來的，`pet` 指令卻作用在現役那隻，
會變成「摸了一隻、爽到另一隻」）。現在改成走 `yardPet` + **內部 id**，
先做命中判定再送，摸到誰就是誰。

- 左鍵摸摸、右鍵開選單，**共用同一份 `yardHit()`** —— 分兩份寫遲早會分叉成
  「右鍵選到 A、左鍵摸到 B」。
- 反應只活在記憶體裡的一個 `Map`，**沒有寫入路徑**，daemon 一關就沒了。
  那正好是它該有的生命週期。
- 連戳判定沿用現役那組門檻（`TOUCH_WINDOW_MS` / `TOUCH_LIMIT` / `SULK_MS`），
  但計數**每隻各自獨立** —— 戳 A 五下不該讓 B 也生氣。
- 反應期間不再跟著 `step` 交替待機幀，否則表情會閃。
- 查不到那個幀名（美術不完整的角色）就退回待機 —— 寧可沒反應，也不要畫出錯幀。

#### 開心 = 原地跳（不移動）

摸到開心的那隻**站住原地上下彈**，不爽的照常走掉 —— 被戳到生氣還在原地蹦，
讀起來像「一邊鬧脾氣一邊很開心」。

**「原地」不能只是把畫的位置釘住。** 走路演算法照跑的話，反應結束會瞬移回它算出來
的位置（1.8 秒約 2~3 dot，每摸一次閃一下）。所以把停走的拍數累加成 `holdSteps`，
之後一律從 `joinStep` 扣掉：對走路演算法而言，這隻的時間在跳躍期間是停的，
落地後無縫接回。

⚠️ `holdSteps` 是那隻的**永久時間位移**，反應演完也要一直帶著回報 ——
丟掉就等於把停走那幾拍還回去，也就是瞬移本身。所以帶著 `holdSteps` 的紀錄
不能被當成「反應結束了」而回收，只有**離開牧場**才收。

跳躍的節奏：上、下各 250ms。**這個數字被前端的輪詢間隔綁死** —— 畫面就只有
`1000/POLL_MS` fps，騰空短於一次輪詢就會整個被取樣漏掉（有時候看得到、有時候看不到，
最難查的那種）。所以 `JUMP_MS` 與 `POLL_MS` 放在同一個檔案（`yard-touch.js`），
前端從那裡取值，測試也直接釘住 `JUMP_MS >= POLL_MS`。

第一版是 500ms，看起來太久、像慢動作停在半空；縮短騰空就得連輪詢一起加快，
所以院子的輪詢從 500ms 改成 250ms（家裡維持 500ms —— 沒有這個需求，
不必為了沒人在看的畫面多打一倍的請求）。

實測那多出來的一倍請求：`composeYard` 2.73ms + 序列化 0.01ms，每秒 4 次約
**11ms/s（一顆核心的 1.1%）**，payload 14.8 KB → 59 KB/s，全在 localhost。
而且只有院子分頁開著時才跑，分頁切到背景時瀏覽器本來就會把計時器降到 1 秒以上。

順帶把 `setInterval(poll, 500)` 改成「上一次結束才排下一次」：間隔縮短之後，
`/yard` 偶爾比間隔慢就會讓請求疊在一起，畫面反而更頓。

相位從按下去那一刻起算，所以第一幀就是騰空的（`sendCmd` 對 `yardPet` 會強制刷一次，
不然要等最多一個輪詢才看得到）。

**只跳一下**（`JUMP_HOPS = 1`）：蹦一下就落地，剩下的反應時間站著把 HAPPY 演完。
第一版是跳到反應結束（1.8 秒約 2 下），看起來比較像在原地蹦跳不停，
而不是「被摸了很高興」。要調就改 `JUMP_HOPS`，測試跟著那個常數走。

跳躍只影響**畫在哪**：`y` 仍是地面位置，y 排序與名牌都用它。跳起來就切到別人前面、
名牌跟著飛，兩個都不對。貼著上緣時往上頂會超出畫面，所以夾住 —— 那一下看不到跳，
很少見，可接受。回傳給前端的 `pets[].y` 則是**畫出來**的位置，因為前端拿它做命中
判定，用地面 y 的話跳到最高點時點身體會落空。

狀態機抽成 `src/daemon/yard-touch.js`，唯一的理由是**可測試**：`daemon.js` 一
`require` 就 `server.listen`，測試載不進來，而上面這些帳（累加、結清、跨反應保管）
最不該只靠肉眼在瀏覽器上驗。時間一律由外面傳進來，測試不用真的等 1.8 秒。
`scripts/test-yard-touch.js` 驗過拿掉任一條會紅（丟掉 `holdSteps` / 不爽也跳 /
連摸重設計時 / 沒接進 `joinStep` / 拿掉上緣夾住，各自 4~5 條失敗）。

📌 寫測試時踩到兩個「假綠」，值得記著：
1. `step` 沒有從 `plaza.yardJoinStep()` 起算 → `step - joinStep` 是負的、夾成 0，
   每一拍都算出同一個起點，斷言全變成拿同一張圖跟自己比。
2. 上緣夾住那條只掃 300 拍，那隻根本沒走到 y < 9 → 拿掉夾住照樣綠。
   現在多一條 `near > 0` 先確認掃描範圍真的涵蓋到貼邊的情況。

### 按鈕分區

前線的鈕多半是對「現役那一隻」下指令（卡片、進化樹、睡覺、重抽…），在牧場畫面按了
只會影響一隻根本沒顯示在畫面上的桌寵 —— 那比按鈕消失更難懂。所以每顆鈕標 `scope`：
`home`（只在前線）或 `both`。牧場相關的四項、圖鑑、doctor 是 `both`。
- y 排序、名牌固定在腳下、逐字遮擋
- **不畫名牌。** 52 dot 寬塞 8 隻，名牌會互相擠掉一半（實測平均 3.5/8 看不到），
  而且名字疊在一起比沒有還難讀。要知道是誰就**在牠身上按右鍵**。
  省下來的名牌保留區（2 dot）直接還給可走範圍。
- **NPC 關掉**（`opts.npc = false`）—— 院子裡不該有野生 vpet 亂入，
  這個開關就是為此預留的
- **不鋪底圖。** 那張 `bg.png` 是為家裡 52×8 的橫幅舞台烘的（`center/cover`），
  放到 96×24 會被裁成完全不同的一塊，看起來像另一張圖。等院子有自己的美術再說。

差異只有名單來源：廣場是伺服器發的在場名單，院子是本機 `ranch.json`。

**seed 從哪來**：每隻的 `id` 雜湊成 seed。不需要伺服器分配（那是廣場為了跨 client
一致才需要的），本機自己算就好，而且同一隻每次開院子的走位都一樣。

現役那隻**不**出現在院子裡。草案原本寫「要，不然院子會像少了一隻」，那是搞混了兩件事：
院子是「收起來的那些」，現役正在你身邊過生活、不在冰箱裡。兩邊都出現的話，
反而看不出「收進去」和「拿出來」的差別。

因此牧場空的時候院子就是空的（`composeYard` 回 `null`），畫面改顯示一行提示而不是
一張空舞台 —— 空舞台看起來像壞掉。

## 五、進化條件掛牧場

讓蒐集回頭餵養成。新增三個條件型別：

| 型別 | 意思 |
|---|---|
| `ranch_count` | 牧場裡有 N 隻以上 |
| `ranch_has` | 牧場裡有特定角色 / 特定 stage / 特定 tag |
| `ranch_species` | **不重複**的種類數達 N（獎勵蒐集廣度，不是數量） |

三個必須處理的問題：

**1. `evalCondition` 要多吃一個參數。** 現有條件全部只讀 `st`（現役那一隻的狀態）
與 `input`；牧場條件要讀另一個檔案。這會同時動到 `agumon-core.js` 和進化路線編輯器
（`src/editor/route_editor_server.js` + `src/shared/evo-rules.js`），不是加一個
`case` 就好。

**2. 一律 latch（達成過就算數）。** 現有條件裡 `power_at_least` / `win_rate` 是即時的
（所見即所得），`r5h_peak` / `cost_threshold` 是 latch 的。牧場條件如果做成即時，
玩家把那隻換出來就會失去資格，會遇到「剛剛明明可以進化」。latch 沒有這個問題。

**3. 只能用在後段分支或彩蛋線，絕對不能擋主線。** 新玩家的牧場是空的，任何掛牧場的
條件在他退休第一隻之前都走不到。另外進化路線編輯器有死路分析，它得認得這些新型別，
否則會把整條線誤報成死路。

## 六、與既有系統的交互

### PvP

**戰卡永遠是「當前取出的那隻」**，要用誰是玩家的自由。

**`swap` / `keep` 之後不需要特別重傳戰卡。** 草案原本寫「必須重傳」，是想錯了：
`vpet pvp` 在配對前本來就會 `PUT /card/<code>` 上傳當前的卡，`vpet code` 改名牌時
也會重傳，所以只要玩家有在打 PvP，卡就是新的。

更重要的是**這個「過時」本來就存在，與牧場無關** —— 練了訓練值、甚至進化了，在下次
打 PvP 之前，別人挑戰到的一樣是舊卡。非同步幽靈對戰的卡本來就是快照。swap 只是讓
落差可能一次比較大，性質相同，而且下次一打就自己修正。

反過來說，為此在 swap 塞一次網路請求是有壞處的：swap 是純本機操作，接了之後沒網路
或後端掛掉時要嘛卡住、要嘛得吞錯誤 —— 為一個會自我修正的問題增加失敗點。

這確實讓玩家可以「停一隻滿等的、養新的、打 PvP 前換回來」。這是刻意接受的 ——
本作偏單機蒐集，養每一隻的時間成本是真的。

### 圖鑑

`album.json` 記的是「你養過誰」（角色 id → 首次取得時間），與牧場是不同維度：
圖鑑是**種類**的紀錄，牧場是**個體**的收藏。兩者並存，不合併。

`keep` / `release` 都不影響圖鑑 —— 放生了也還是養過。

### reset

不變。`reset` 丟掉重抽，`keep` 保留重抽。

### hook / 成長

牧場裡的凍結，代表 hook 的訓練值、自動戰鬥、活動時戳**只作用在現役那一隻**。
這是自然結果（那些都寫在 `state` 的現役欄位上），不需要額外的 gate ——
與廣場「不在家要暫停飼育」不同，那邊才需要特別擋。

### 多視窗 / daemon 當家

`ranch.json` 的寫入時機只有 keep / swap / release 三個明確動作，不在每秒 tick 上，
所以沒有多視窗競寫的問題。但**交換會同時改 `ranch.json` 與 `color-state.json`**，
兩個檔要一起換 —— 中途失敗會導致同一隻同時在冰箱裡和手上（或兩邊都沒有）。
用既有的 `atomicWrite`，並且**先寫 ranch 再寫 state**：這個順序下最壞的結果是
「牧場多一份、現役沒換成」，玩家看得到也救得回；反過來則是桌寵消失。

## 天氣（階段 2.5）

牧場右上角顯示日期／時間／天氣，場上依天氣做表演。

### 資料模型：sky + cold，不是五選一

需求列的是「晴／陰／雨／大雨／寒流」，但**寒流是氣溫、不是天空狀態** ——
台灣冬天「寒流 + 下雨」是常態，做成五選一那天只能二選一，之後要加颱風、起霧
也得回頭改結構。所以拆成：

| 欄位 | 值 |
|---|---|
| `sky` | `clear` / `cloudy` / `rain` / `storm` / `thunder`（嚴重度階梯） |
| `cold` | 布林，氣溫 ≤ `coldBelowC`（預設 12°C） |

**判準：這兩件事會不會各自單獨發生。** 晴天也會冷 → 寒流是獨立旗標。
打雷一定伴隨下雨 → 雷雨不是旗標，是同一個軸上更嚴重的一格（雨 → 大雨 → 雷雨）。
WMO 本來就分得很清楚：95/96/99 是雷雨，63/65/81/82 是沒有雷的大雨。

`describe()` 把寒流當**加註**：`陰・寒流`，不是取代天空狀態。

12°C 的由來：氣象署的寒流定義是台北測站 ≤ 10°C，但那一年只有幾天、做了幾乎看不到；
12°C 約等於「強烈大陸冷氣團」，一個冬天出現幾次 —— 夠特別又不會永遠見不到。

### 天氣來源：Open-Meteo

`src/daemon/weather-source.js`。這是 **daemon 第一個對外的連線**（在此之前只有
localhost），所以規則寫死：

1. 只打 Open-Meteo 一個網址，免 API key、免註冊。
2. **不做 IP 定位。** 座標寫在 `<INSTALL_ROOT>/weather.json`，預設台北。
   為了猜位置把 IP 送去第三方，為了一個天氣效果不值得。
3. 抓不到就沉默退回晴天並標記 `stale`（右上角顯示「離線」）。
   天氣是裝飾，**絕不能因為公司擋 proxy 或斷網就讓牧場開不起來**。
4. 30 分鐘抓一次，而且是背景抓 —— `get()` 永遠立刻回傳快取，`/yard` 這條路徑不等網路。
5. `weather.json` 的 `"enabled": false` 可以整個關掉連線。

快取同時落地到 `state/weather-cache.json`：daemon 重開不該馬上再打一次，
開發時反覆重啟尤其明顯。

**快取存的是「觀測」不是「判定」** —— 只留 `code` / `tempC` / `at`，每次 `get()`
才用當下的對照表與設定重新判定。第一版存的是判定結果（`sky` / `cold`），
加雷雨的時候立刻踩到：WMO 95 從 storm 改判 thunder，畫面卻照樣是大雨，
因為快取裡寫死了 `sky:"storm"` —— 而且快取落地，**重開 daemon 也救不回來**，
要等 30 分鐘下一次抓取。症狀是「程式改了、測試也綠、畫面沒變」，最難查的那種。
同理，改 `weather.json` 的 `coldBelowC` 現在也立刻生效。

（舊快取檔不需要遷移：它本來就含 `code` / `tempC`，讀進來直接用新對照表重判。）

### 表演全在前端，而且不動角色顏色

第一版做了「色調層」：在後端的 dot 緩衝上依天氣調明暗冷暖，貼完角色才染，
所以陽光會照在怪身上、寒流會把怪凍得發青。**實際看過之後整層拿掉了** ——
角色點陣圖只有 16×16、顏色本來就少，一染就分不出誰是誰，而且「我的亞古獸今天是藍的」
比氣氛加分更讓人困惑。連帶結論：`shared/weather.js` 現在是純粹的「天氣是什麼」，
不含任何繪圖；`composePlaza` 也不再收 `opts.weather`。

所以天氣**只有粒子層**，跑在前端 rAF。為什麼不放後端：`/yard` 是 500ms 輪詢、
走路 750ms 一拍，用那個節奏畫雨會變成一格一格瞬移的點，完全不像下雨。

雨滴用固定種子起始（重整看到同一場雨），但**不需要跨 client 一致** ——
沒有人分得出你我的雨滴有沒有對齊，所以接廣場時這段原封不動就能用。
走路那邊不一樣，那個必須逐拍決定性（見 `shared/plaza-walk.js`）。

### 五種表演

| 天氣 | 做法 |
|---|---|
| 晴 | 斜射光柱緩慢飄移，`lighter` 疊加（只加亮不遮擋，光線蓋住角色會很怪） |
| 陰 | 上緣薄雲飄過 |
| 雨 | 雲變厚變快 + 落雨 |
| 大雨 | 雨的加強：密度 40→110、速度 175→300、雨絲更長更斜 |
| 雷雨 | 大雨再加強（150 / 360）＋ **閃電** |
| 寒流 | 少少幾陣「捲」橫著吹過，**疊加**在任何天空狀態上 |

冷風走過四版，每一版都是看了畫面才知道錯在哪：

1. 26 條細直線、alpha 0.05~0.17 → 等於看不見，回報「寒流沒顯示」。
2. 40 條加粗加亮 → 看得見了，但**變成流星雨**。密集的直線一律被讀成「掉落物」，
   跟它是水平還是垂直無關。
3. 5 陣向量畫的螺旋 → 風要靠**形狀**認不是靠數量，這點對了；但它是畫面上唯一的
   平滑曲線，**跟滿場的像素格格不入**。形狀對了還是不對。
4. **5 陣天狐獸子彈的點陣**（本版）→ 直接借現成的美術。

第 4 版的關鍵在於「借」而不是「畫」。天狐獸的子彈本來就是一團青色的風：
中心亮、外圍青、周圍散著幾點閃光 —— **那幾點閃光是造型的關鍵，自己畫很難拿捏**。
而且它是點陣，總算跟場景講同一種語言。

做法：伺服器端 `loadWindArt()` 把 `tenkomon/bullet-art.json` 抽成依顏色分組的
`[{c:'rgb(...)', p:[x,y,...]}]`（3 組 / 49 dot / 290 bytes），內嵌進頁面；
前端每 dot 畫一個方塊。分組是為了每幀只設 3 次 `fillStyle` 而不是 49 次。
起點與 dot 尺寸都取整數，方塊才會對齊像素格、邊緣不被反鋸齒糊掉。

- 尺寸對著角色抓：畫布 416×320、角色 128px 高；每 dot 畫 4~7px → 一陣風 40~70px，
  約角色的一半。
- 美術不在（換過角色表、精簡過 release）會退回一小團青色方塊 —— 形狀差一點，
  但不會讓牧場開不起來。

⚠️ **造型有方向性，吹的方向必須跟圖一致。** 子彈的散點是拖在尾巴上的，
第一次接的時候風往左吹、圖卻朝右（原圖是角色朝右發射的），尾巴跑到前面去 ——
一眼就看得出怪。現在由 `WIND_DIR` 一個常數同時決定移動方向與要不要鏡射
（`+1` = 由左至右、不鏡射；`-1` = 由右至左、鏡射），不可能再對不上。
目前是 **`+1`，由左至右**。

⚠️ **閃電**畫在所有粒子之後（蓋住整個畫面，才像整片天空亮起來），做成**雙閃** ——
0~70ms 主閃、130~230ms 較弱的第二下，中間暗下來。一路線性淡出只會像畫面在呼吸。
峰值壓在 0.28、間隔 5~13 秒隨機：場地只有 416×320，整片白閃很容易變成騷擾。

雨傘圖示讓給大雨、閃電雲圖示給雷雨（它才是「有閃電的雨」）—— 有測試釘住兩者不可同圖示。

**與原始需求的偏離**：需求寫「雨＝最上方一些淺淺的雨」，實作改成**整片**由上落下。
只在上緣下雨看起來像天花板漏水，不像下雨；改用低透明度控制存在感，角色一樣看得清楚。
要改回去就把雨滴 `y` 的範圍夾住。

密度／速度全部集中在 `WXR` 常數。場地只有 52×20 格（416×320px），粒子多一點畫面就會
爛成雜訊、看不出誰是誰 —— 一律保守。

雨滴池的大小**從 `WXR` 推出來**（`Math.max(...)`），不要寫死。寫死 120 而雷雨要 150
就踩過一次：迴圈讀到 `P.drop[120]` 是 `undefined` 直接丟例外，而例外發生在雲畫完之後 ——
**「雷雨」看起來就跟陰天一模一樣**。`requestAnimationFrame` 在 `wxDraw` 開頭就排好下一幀，
所以它每幀照丟，畫面不會停、也不會有任何徵兆。

### 前端要實跑才測得到

上面那個 bug 語法檢查抓不到（語法完全正確），伺服器端測試也抓不到（後端一切正常）。
`scripts/test-daemon-page.js` 因此多了一段**headless 實跑**：把頁面的 script 丟進 `vm`、
配一套假的 canvas 記錄畫了什麼，然後跑過 5 種天空 × 冷/不冷，斷言

- 每一種都能畫完整幀而不丟例外，
- 雨量隨嚴重度遞增（只驗「沒丟例外」的話，把密度打成 0 也會過），
- 寒流有畫出冷風、雷雨有閃電。

驗證過它會抓到修正前的版本（26 passed / 4 failed）。這是第二個「伺服器完全正常、
只有瀏覽器死掉」的 bug（第一個是 template literal 吃掉跳脫字元），所以值得這套探針。

### 天氣預覽（dev 專屬）

天空用下拉、**寒流是獨立的勾選框**。它跟天空正交，混進同一份清單會讓人以為「寒流」
是某種天空，也組不出「陰・寒流」「雨・寒流」那類**台灣冬天最常見**的情況
（晴・寒流反而少見）。網址端同樣不規定順序、不規定要不要指定天空：
`?w=cold` = 真實天空 + 強制寒流、`?w=cold+rain` = `?w=rain+cold`。

`/yard?w=rain`、`?w=storm+cold`，牧場工具列有下拉選單。**只影響回傳的畫面**，
不寫檔、不影響真實天氣的抓取。沒有這個，五種表演要等真的下雨才看得到。
未知的值一律忽略、退回真實天氣。

跟其他 dev 功能同一條規矩：**只把 UI 藏起來是不夠的**，`/yard` 是公開端點，
`IS_RELEASE` 時伺服器端也要擋，否則 release 版照樣能用網址切天氣。

⚠️ **查詢字串裡的 `+` 會被解碼成空白。** 前端忘了 `encodeURIComponent`，
`clear+cold` 到伺服器端就變成 `"clear cold"`，比對不到 → 整個退回真實天氣。
症狀是「選了寒流卻什麼都沒發生」，而畫面其他部分完全正常，很難聯想到是網址編碼。
兩邊都修了：前端編碼，伺服器端分隔符同時吃 `+` 與空白（有人會直接在網址列手打）。
`scripts/test-daemon-page.js` 兩種寫法都驗。

### 右上角看板

用 HTML 疊層（`#hud`）而不是畫點陣字：52 dot 寬塞一整行日期會佔掉整列又糊掉，
而且這本來就不是像素風的一部分，是「看板」。時間走本機時鐘每秒自己跳，
不跟著 `/yard` 輪詢 —— 斷線時時鐘不該跟著停。

天氣畫布（`#wx`）疊在角色畫布正上方，`pointer-events:none` 是必要的，
否則它會吃掉右鍵選單的命中判定。角色畫布每次 `draw()` 都依內容重建尺寸，
所以每次畫完都要 `syncWx()` 重新對位。

## 走路：貼牆時的處理（`shared/plaza-walk.js`）

回報「牧場滿有機會卡在邊界」。**不是卡住，是在原地抖。**

真因：貼著牆的時候，「幾乎與牆平行、但帶一點朝外分量」的方向會被 `fit()` 截成
1~2 拍 —— 角色每一兩拍就重抽一次方向，走一格、換方向、再走一格。牧場場地小
（可走範圍只有 37×25），這件事特別明顯。

修法：抽到的方向被截得太短（< `MIN_LEG` = 5）就**換一個方向**，而不是硬走那一兩拍。
掃描從抽到的那個方向開始、以與 32 互質的步長（7）跳，所以會走遍全部 32 個方向而
不偏袒任何一邊；起點仍由亂數決定，路線多樣性不受影響。32 個方向都走不滿就走最長的
那個，真的動不了才算「停」。全程只用整數與 seed，**決定性不變**（廣場要用的前提）。

### 第二版：撞牆就往外走

第一版只解掉抖動，**貼邊時間完全沒降**（19.2% → 19.1%）。當時判斷那是刻意設計
（「走到牆邊就停、下一段重新抽方向」），但實際看畫面還是覺得黏在邊界 —— 因為
「重新抽的方向」可以是**沿著牆滑**的方向，而且有 1/4 機率抽到「停」，就站在牆邊發呆。

所以再加兩條，都是**無狀態**的（只看當下座標，決定性不變）：

1. **貼在牆上時，方向必須離開那面牆。** 掃描分兩輪：第一輪要求離開牆，
   找不到才拿掉這個要求當退路（角落或極小場地可能真的沒有）。
2. **貼在牆上時不抽「停」。** 站在牆邊 4~8 拍是「卡在邊界」體感最大的來源；
   一般位置照舊有 `STAY_CHANCE` 的機率停下來發呆。

實測（8 隻 × 8000 拍，牧場）：

| | 原始 | 加 `MIN_LEG` | 再加「撞牆往外走」 |
|---|---|---|---|
| 段長 ≤ 3 拍 | 9.5% | 0% | 0% |
| **貼邊時間** | 19.2% | 19.1% | **5.2%** |
| **在牆邊發呆** | 有 | 有 | **0%** |
| 最熱一格 / 平均 | 4.3 倍 | 3.3 倍 | **2.0 倍** |
| 最熱一格 / 平均（廣場） | 4.8 倍 | 4.0 倍 | **2.6 倍** |
| 停留時間 | 14.3% | 12.1% | 5.4% |

⚠️ **停留時間掉到 5.4%** 是這一版的副作用：很多段是在牆邊結束的，而那些段結束後
一律不抽停 → 整體停下的機會少很多。方向上跟先前「減少角色停下的頻率」一致，
覺得太少就調 `STAY_CHANCE`（目前 1/4）。

`scripts/test-plaza.js` 釘住四條：最短移動段 ≥ `MIN_LEG`、最熱一格 < 3.5 倍平均、
**牆邊發呆必須是 0**、貼邊時間 < 8%。門檻都是量出來的（見上表），
驗證過拿掉任一條會紅（49 passed / 5 failed）。

### 第三版：開機超過 41.7 小時全員定格

回報「牧場的腳色不會移動了」。**不是走路演算法的問題** —— 同一組 seed 在測試裡跑
600 拍動了 551 拍。是 `posAt` 的保險寫錯了對象：

```js
const target = Math.min(MAX_REPLAY, Math.max(0, step - joinStep));   // ✗
```

`MAX_REPLAY`（200000 拍）本意是「一次呼叫最多重播幾拍」，防的是 joinStep 傳錯
（yard 曾把它寫死成 0，而 step 是牆鐘算出來的 24 億，同步迴圈直接把 daemon 卡死）。
但它 clamp 的是**目標拍數**而不是**重播距離** —— 超過之後 `target` 就不再成長，
所有人的位置永遠停在第 200000 拍，而畫面右上的 tick 照跳。

200000 x 750ms = **41.7 小時**。院子的 `joinStep` 是「daemon 這次啟動的時間」，
而 daemon 一開就是好幾天，所以這條路徑不是理論上碰得到，是**必然**會碰到。
實測發生時開機 63.7 小時，三隻分別停在 27,1 / 20,1 / 25,12 —— 其中 20,1 正好等於
`posAt(seed=646533808, t=200000)`。

改成 clamp 重播距離：

```js
const target = Math.max(0, step - joinStep);
const usable = cache && cache.at <= target && target - cache.at <= MAX_REPLAY;
let st = usable ? { ...cache }
                : { ...startPos(seed, field), k: 0, at: target > MAX_REPLAY ? target : 0 };
```

有快取（＝ daemon 每 500ms 輪詢的正常路徑）就完全不受上限影響，跑再久都照走。
上限只管沒有快取的冷啟動，超過就當作「這隻現在才進場」。

⚠️ 中間試過「起點拉到 `target - MAX_REPLAY`」，看起來比較講理，其實**一樣定格**：
走位鏈只由 seed 與 k 決定，每次都重播剛好 `MAX_REPLAY` 拍就永遠得到同一個位置，
還白花 6ms。不重播反而是對的。

測試釘住三件事：跨過上限之後 400 拍要動 > 300 拍、冷啟動位置要在場內、
joinStep 傳錯時 `posAt` 要在 50ms 內回來（原始那個 bug 的成因不能復活）。
驗證過還原成 `Math.min(...)` 會紅。

## 牧場相關進化：規則型特殊進化

第一條是大便獸彩蛋 —— 原作疏於照顧會變大便獸，而我們省略了餵食／清掃／關燈，
所以改用「丟在牧場完全不動 48 小時」當替代。**不可逆、可出戰、視為一種進化**
（`power: 50`）。

### 為什麼不寫進 `config.evolvesTo`

roster 目前有 **19 隻 Child**。照一般做法就是 19 個 `config.json` 各加一條邊，
那會同時汙染三個地方：

| 受害處 | 症狀 |
|---|---|
| `vpet tree` / 圖鑑 | 19 條線收斂到同一顆 |
| 進化路線編輯器 | SVG 圖多 19 條交叉線 |
| `parentsOf()`（`agumon-core.js`） | 大便獸有 19 個 parent，血緣長度（tree 格數）會很奇怪 |

而且每新增一隻 Child 就要記得補一條，遲早漏掉。

改寫成**一條規則**之後，那三個地方**一行都不用改** —— 它們讀的是 `evolvesTo`，
看不到規則就自然不會畫。要露出來走反方向：在大便獸自己的圖鑑頁寫
「來源：幼年期在牧場放置 48 小時」，一行字取代 19 條箭頭。

### 檔案：`characters/special-evolutions.json`

```json
{ "rules": [
  { "id": "sukamon-neglect", "to": "sukamon", "fromStage": "Child",
    "conditions": [{ "type": "ranch_hours", "hours": 48 }], "hidden": true }
]}
```

⚠️ **不要搬進 `roster.json`。** 進化路線編輯器存檔時會**整份重寫** roster.json，
而且只寫 `roster` / `starters` / `starterWeights` / `highTierStarters` 四個 key
（`route_editor_server.js:273`）—— 加在那裡會在下次存檔時被無聲刪掉。

### 「完全不動 48H」不需要任何新狀態

`keptAt` 已經正好是這個語意：`keep` 和 `swap` 都是 `keptAt: Date.now()` 新開一筆，
而被換出來的那隻是**整筆從 ranch 移除**（`splice`）—— 之後再收進去是全新 id、
全新 `keptAt`。所以判定就是 `now - keptAt >= 48h`，中途取出自然歸零。

計時是**每隻獨立**的：取出 A 不會重置 B。反過來做的話「多收一隻，其他七隻的進度
就沒了」，那不合理。

### 惰性判定，不是計時器

牧場是冰箱、裡面的東西不會自己長大，這是唯一的例外。用 `keptAt` 現算，所以 daemon
關掉的那段時間照樣算數 —— 你下次打開牧場才發現牠變了，那正好就是「默默變成」
該有的體感。

放在 `applyForceFlags` 而不是 `/yard`，是為了維持 **ranch.json 的單一寫入者** ——
`applyForceFlags` 只有當家那一端會跑（daemon 是 `if (AUTHORITATIVE)`），`/yard` 純讀不寫。
節流 `RANCH_AGE_CHECK_MS = 60s`：這條路徑每拍都會經過，48 小時的判定不需要每秒重算。

⚠️ **必須排在讀 `force-char.json` 之前。** 第一版放在後面，而那個 `JSON.parse` 失敗
就整個 `return` —— 「force-char.json 不存在」是完全正常的狀態（全新安裝、或從沒下過任何
vpet 指令），結果就是**牧場永遠不會老化**。測試全綠、真機上放了 Child 進牧場卻永遠不變，
就是這個。老化跟 force 檔一點關係都沒有，不該共用同一條錯誤路徑。已加測試釘住。

### 三個一定要做對的細節

**圖鑑要另外登錄。** `recordAlbumIfChanged()` 看的是**現役**的 `characterId`，
而大便獸是在冰箱裡變的、從頭到尾沒當過現役 —— 走那條路永遠不會被收錄。
所以另外開了 `recordAlbumChar(id)`，在變成的當下就登錄（彩蛋的獎勵是「你看過牠了」，
那一刻就該給）。

**血緣要自己接上。** 不處理的話，之後換出來時 `updateEvoHistory` 會發現
「大便獸不是前一隻的 `evolvesTo` 目標」而判定為斷點，把整條 `evoHistory` 清成單一顆，
`vpet tree` 的格數就沒了。既然定位是「視做一種進化」，血緣就該留著。

**要顯示原本是誰。** ranch entry 存 `evolvedFrom`，CLI 清單顯示「大便獸（原：亞古獸）」、
daemon 右鍵選單同樣。全藏起來的話玩家會以為自己的收藏不見了而恐慌 ——
那是 bug 的體感，不是彩蛋的體感。

### 安全邊界

- **未知的條件型別一律不成立。** 寧可不觸發，也不要因為看不懂就亂把人家的收藏變掉。
- **目標不在 roster 就不生效**（與 `checkEvolution` 同一條 gate）。所以規則可以先寫好，
  等美術進 roster 才會真的開始變 —— **大便獸現在就是這個狀態，是惰性的**。
- 已經是目標角色的不再觸發（大便獸是 Adult，`fromStage: Child` 本來也擋得住，
  但這條防呆讓「日後有人順手放寬條件」不會變成無限迴圈）。

### power 50 的兩個副作用

- `stageForPower()` 的 Adult 容忍下界正好是 `55 - 5 = 50` —— **50 剛好踩在線上**，
  49 就會被判成別的階。要調的話記得一起看 `BAND`。
- 現役 Adult 最低是 55（gatomon / coelamon），所以大便獸是**最弱的成熟期**，
  符合它的定位。但 Child 的 `TIER_CAP` 也是 50 —— 對一隻沒練過的 Child 來說，
  變大便獸其實是「免費升階、上限從 50 變 100」。48 小時什麼都不做換一隻最弱的
  Adult，代價算合理，但這條路確實繞過了 `cost_threshold` + `win_rate`。

### 美術（已實裝）

`characters/Sukamon/`：12 幀 + CutIn，48×48 PNG（3×3 一格 → 邏輯網格正好 16×16，
符合 char-cli 的要求）。`layout: individual` + `directSample`，所以顏色是原封不動搬過來的
（實測 art.json 的色票與原圖逐色相同，沒有量化損失）。

子彈**先直接沿用亞古獸那顆**（不是 `gen-bullet-placeholders.js` 的暫代白球 ——
那顆一看就是佔位的）。等專屬子彈美術進來再換掉 `characters/Sukamon/bullet-art.json`。

原始檔有幾組幀是同一張圖（Sleep_1 = Sleep_2 = Hurt = Sad、Angry = Attack、
Idle_2 = Eat_2）—— 對一坨大便來說合理，但代表牠**睡覺沒有呼吸動畫、待機也不會動**。
要動就得補圖，程式面不用改。

⚠️ `special-evolutions.json` 不是任何角色的附屬檔案，`installCharacters` 的迴圈掃不到 ——
已在 `installRoster()` 裡單獨帶一份（漏掉的話規則只存在 repo，實際跑的那份看不到）。

### 副作用：Sukamon 在進化圖上是孤兒

牠沒有任何 parent（沒人的 `evolvesTo` 指向牠）也不是 starter，所以路線編輯器的
「無 parent 且非 starter」清單會有牠。**這是預期的** —— 那正是不寫 19 條邊換來的。
牠是可達的，只是可達路徑不在 `evolvesTo` 裡。

死路檢查確認過：加入前後都是 0。

### 待辦

- 圖鑑頁的「來源」文字（`hidden` 旗標目前只是資料，還沒有畫面用它）
- 階段 3 原本規劃的另外三種條件（`ranch_count` / `ranch_has` / `ranch_species`）仍未做
- 專屬子彈美術（目前直接借亞古獸的）
